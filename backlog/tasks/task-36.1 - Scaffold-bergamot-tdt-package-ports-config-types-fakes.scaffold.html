1. The module's place in the system

@bergamot/tdt is a new top-level npm workspace package, a sibling of vscode/ and browser/. It is a pure, dependency-injected library plus thin adapters. It depends only on its injected port contracts and on clustering-tfjs. It NEVER imports vscode/src internals.

The root package.json workspaces array today is ["vscode", "browser"]; this slice adds "tdt".

The dependency wall

┌─────────────────────────────────────────────────────────────────────┐
│  vscode/  (the VS Code extension — the SINGLE WRITER of the DB file)  │
│                                                                       │
│   • owns the DuckDB file read-write for its whole lifetime            │
│   • supplies the CONCRETE port implementations                        │
│   • triggers run_tdt(...) and persists results in one transaction     │

Why the wall exists: the DuckDB single-writer constraint

DuckDB is single-writer per file across processes. While the VS Code extension holds the database read-write (it does, for its whole lifetime), no other process can open the file — even read-only. The extension is the only writer. This constraint drives the entire port design.

If TDT opened the DuckDB file directly, the file open would be refused (an availability failure, not corruption — but it still breaks the batch job). So TDT never touches the file. Instead it expresses its data needs as ports, and the extension supplies implementations that go through the writer it already owns:

  • Relational reads go through a RelationalReader port. Production: in-process reader fns when TDT runs inside an extension command; HTTP /query/* when TDT runs as the batch CLI. Never a direct file open.
  • Page vectors are TDT's own, cached in a TDT-owned topic_page_vector table in the same DuckDB file — read/written through the extension's writer, behind the VectorStore port. No second vector store, no LanceDB.
  • Cluster writes go through a ClusterSink port. The write path is owned by the extension's single writer — TDT's compute hands results back, the extension persists them. The batch CLI does read+compute only.

The result is a clean inversion: TDT is testable in pure memory (fakes satisfy the ports), and production wiring lives entirely on the vscode/ side of the wall.

2. The four port contracts

The ports are the injected seams. Every later sub-task is implemented against these interfaces, never against a concrete reader or writer. This is the heart of AC #2: "ports.ts defines RelationalReader, EmbedFn, VectorStore, and ClusterSink with documented contracts, and contains no import from vscode/src."

PortWhat it doesProduction supplierTest supplier
RelationalReader Reads captured visit metadata (URL, title, timestamp, tree id) for a time window from DuckDB. Stage 1 of the pipeline. vscode/ in-process reader fns, or HTTP /query/visits_in_window from the batch CLI in-memory fake over a fixed array of VisitRow
EmbedFn TDT's own local text-embedding model. Maps page text → a raw vector. Has no dependency on the RAG pipeline (task-31). vscode/ a local model adapter (e.g. a 384-d sentence encoder via @xenova/transformers) in-memory fake deterministic hash/stub vectors
VectorStore The page-vector cache: get/put one L2-normalized vector per (page_session_id, embedding_model_id). Backs the topic_page_vector table so re-runs skip re-embedding and a model change invalidates cleanly. vscode/ DuckDB-backed cache through the writer in-memory fake a Map
ClusterSink The write port: accepts (run, clusters, members) and persists them. TDT computes; the sink owns the actual DuckDB write transaction. vscode/ the single-writer transaction over topic_run / topic_cluster / topic_cluster_member in-memory fake records the last write for assertions

The shape these contracts take in ports.ts

The task spec fixes the names and responsibilities; the exact method signatures are this sub-task's design work, constrained by the stage types in §3 and the data flow in the design doc. A faithful skeleton:

// ports.ts — NO import from vscode/src. Pure contracts.
import { VisitRow, RepresentedCluster } from "./types";

/** Reads captured visit metadata for a window (Stage 1).
 *  Production: in-process DuckDB reader OR HTTP /query/visits_in_window.
 *  Rows MUST arrive ORDER BY page_loaded_at, page_session_id (determinism anchor). */
export interface RelationalReader {
  listVisitsInWindow(start: string, end: string): Promise<VisitRow[]>;
}

/** TDT's own local embedding model (NOT RAG's). page text -> raw vector. */
export type EmbedFn = (texts: string[]) => Promise<Float32Array[]>;

/** Page-vector cache, keyed (page_session_id, embedding_model_id). */
export interface VectorStore {
  get(pageSessionId: string, modelId: string): Promise<Float32Array | null>;
  put(pageSessionId: string, modelId: string, vector: Float32Array, repr: string): Promise<void>;
}

/** Write port. TDT computes; the sink owns the single-writer transaction. */
export interface ClusterSink {
  write(run: TopicRun, clusters: RepresentedCluster[], members: ClusterMember[]): Promise<void>;
}

The exact field set on TopicRun / ClusterMember is shaped by the persistence schema (design doc §8) and finalised when persistence lands (task-36.6). For 36.1 they need only be sufficient for the fake sink to record a no-op write. The four names and roles above are the load-bearing commitment.

3. The shared stage types (§6)

These are the data shapes that flow between pipeline stages. They live in types.ts and are part of AC #4. Reproduced exactly as specified in design doc §6:

// types.ts
export interface VisitRow {
  // Stage 1
  page_session_id: string;
  url: string;
  title: string | null;
  site_name: string | null;
  page_loaded_at: string; // ISO TEXT
  tree_id: string;
}
export interface PageVector {
  // Stage 2 (order preserved from Stage 1)
  page_session_id: string;
  vector: Float32Array; // L2-normalized page vector
  low_confidence: boolean; // multi-topic dispersion / fell back to dominant segment
}
export type DistanceMatrix = number[][]; // Stage 4: dense (n,n), D[i][i]=0, symmetric, [0,2]

export interface HdbscanRaw {
  // Stage 5
  labels: number[]; // -1 = noise
  probabilities: number[]; // [0,1], 0 for noise
  exemplar_indices: Map<number, number>; // clusterId -> single row index (eom + storeExemplars)
}
export interface RepresentedCluster {
  // Stage 7
  local_label: number;
  member_indices: number[];
  representative_index: number; // exemplar (eom) else medoid
  representative_vector: Float32Array; // FROZEN: L2-normalized mean of member vectors
  size: number;
  time_span: { start: string; end: string };
}

Note the deliberate snake_case on these field names. These are our types — they match the repo's DuckDB column convention. The clustering library speaks camelCase; §7 explains where that translation gets quarantined.

4. The config shapes (§5)

AC #4 requires config.ts to expose DEFAULT_WINDOW_CONFIG and DEFAULT_HDBSCAN_CONFIG. The window config is fixed exactly by design doc §5:

WindowConfig + DEFAULT_WINDOW_CONFIG (§5, verbatim)

export interface WindowConfig {
  unit: "month" | "days";
  days?: number; // when unit==='days'
  tz: "UTC";
  max_samples: number; // 4000: hard count guard, headroom under ~5k
  subdivide_order: ("gap" | "half_month" | "iso_week")[];
  min_window_visits: number; // 8
}
export const DEFAULT_WINDOW_CONFIG: WindowConfig = {
  unit: "month",
  tz: "UTC",
  max_samples: 4000,
  subdivide_order: ["gap", "half_month", "iso_week"],
  min_window_visits: 8,
};

HdbscanConfig + DEFAULT_HDBSCAN_CONFIG (from §6 parameters)

The design doc §6 fixes the HDBSCAN defaults as starting points selected by the validation sweep (task-36.7) and persisted as config — not magic constants. The shape derives directly from the parameter section:

export interface HdbscanConfig {
  min_cluster_size: number;        // pages; a 3-page thread is a real project
  min_samples: number;             // DECOUPLED from min_cluster_size
  method: "eom" | "leaf";          // eom = stable + has defined exemplars
  epsilon: number;                 // cosine-distance units
}
export const DEFAULT_HDBSCAN_CONFIG: HdbscanConfig = {
  min_cluster_size: 3,   // §6: a 3-page thread is a real personal-scale project
  min_samples: 5,        // §6: decoupled; under-smoothing causes chaining + label flips
  method: "eom",        // §6: most stable; the method exemplars are defined under
  epsilon: 0.0,        // §6: swept {0.0, 0.10, 0.20}
};

Why these are defaults, not constants. Per §6, the operating point is chosen by the validation sweep (task-36.7) on real data and persisted as config, parameterized by window size. Re-tuning as history grows is a data change, not a code change. 36.1 only establishes the shape and a sane starting value.

6. What "no-op run_tdt round-trips fakes" means

This is AC #3, the central acceptance test of 36.1. It proves the seams compose before any real stage exists. Concretely:

  1. Construct a deps object built entirely from the in-memory fakes: a fake RelationalReader (returns a fixed array of VisitRow), a fake EmbedFn (returns deterministic stub vectors), a fake VectorStore (a Map), and a fake ClusterSink (records what it was asked to write).
  2. Call run_tdt(deps, args) with some minimal args (e.g. a window range + default config).
  3. The no-op orchestrator wires the ports together in the right shape — it accepts the deps, can touch each port without throwing, and returns a well-typed result — but performs no real clustering. Later sub-tasks fill in the stages; 36.1 just proves the plumbing type-checks and runs.
  4. The test asserts the round-trip completes: the reader was consulted, the sink was reached (even with an empty/trivial payload), and the return type matches.
// test/run_tdt.noop.test.ts (sketch)
import { run_tdt } from "../src";
import { makeFakeDeps } from "../src/fakes";

test("no-op run_tdt round-trips the fakes", async () => {
  const deps = makeFakeDeps({ visits: [/* a few VisitRow */] });
  const result = await run_tdt(deps, { window: { start: "2026-05-01", end: "2026-06-01" } });
  expect(result).toBeDefined();
  expect(deps.sink.lastWrite).not.toBeNull();  // the sink was reached
});
The point

The DI seams are real and composable from day one. Every later stage slots in behind a port that already has a fake, so each sub-task is unit-testable in isolation without VS Code, DuckDB, or a network.

7. The camelCase ↔ snake_case boundary

The task description says: "Quarantine the clustering-tfjs camelCase↔snake_case naming translation inside this package boundary." Here is exactly what that means.

Two naming worlds meet at @bergamot/tdt:

WorldConventionExamples
clustering-tfjs (the library)camelCaseminClusterSize, minSamples, clusterSelectionMethod, clusterSelectionEpsilon, storeExemplars, labels_, probabilities_, exemplarIndices_
Bergamot / TDT (our types & DuckDB)snake_casemin_cluster_size, page_session_id, page_loaded_at, exemplar_indices, representative_vector

Quarantine means: the camelCase ↔ snake_case translation happens in exactly one place — the boundary inside this package where TDT calls the library — and nowhere else. Our config (DEFAULT_HDBSCAN_CONFIG with min_cluster_size), our types (HdbscanRaw.exemplar_indices), and our persistence are all snake_case. The only spot that knows the library's camelCase is the call site, which maps our snake_case config into the library's camelCase options and maps the library's camelCase results back into our snake_case types.

   our snake_case world                  the ONE quarantine boundary           clustering-tfjs camelCase world
 ───────────────────────                ─────────────────────────────         ───────────────────────────────
 DEFAULT_HDBSCAN_CONFIG  ──┐
   min_cluster_size: 3      │  translate snake_case -> camelCase
   min_samples: 5           ├──────────────────────────────────────►  new HDBSCAN({ minClusterSize, minSamples,
   method: "eom"            │  (cluster_window.ts, task-36.4)               clusterSelectionMethod, ... })
   epsilon: 0.0            ─┘                                                       │
                                                                                    │ model.fit(D)
                                                                                    ▼
 HdbscanRaw          ◄──────  translate camelCase -> snake_case  ◄────────  labels_, probabilities_, exemplarIndices_
   labels                    (same boundary)
   probabilities
   exemplar_indices

For this sub-task (36.1) the actual fit call lands later (36.4), but the contract that quarantines the translation is established now: ports.ts and the config/types are pure snake_case, and they document that the only camelCase the package ever speaks is at the eventual cluster_window.ts call site. Nothing outside that file imports the library or sees a camelCase field.

Why it matters: if camelCase leaked across the package — into persistence, MCP responses, or our types — every consumer would have to know the library's naming, and a library rename would ripple everywhere. Quarantining it keeps clustering-tfjs a swappable detail behind one translation layer.

8. Acceptance criteria checklist

The five ACs from the task doc, with what "done" concretely looks like for each:

  • #1  A new tdt/ workspace is added to the root package.json workspaces array and tsc builds it clean.
    Done = root workspaces is ["vscode","browser","tdt"]; tdt/package.json + tdt/tsconfig.json (extending ../tsconfig.base.json) exist; npm run build in tdt/ compiles with zero errors under strict TypeScript.
  • #2  ports.ts defines RelationalReader, EmbedFn, VectorStore, and ClusterSink with documented contracts, and contains no import from vscode/src.
    Done = all four exported with doc comments stating responsibility + production/test supplier; a grep for vscode/src (or any vscode import) in tdt/src returns nothing.
  • #3  In-memory fakes exist for every port and a no-op run_tdt(deps, args) round-trips them in a unit test.
    Done = a fake for each of the four ports; run_tdt exported from index.ts as the public API; a passing Jest test that builds deps from fakes, calls run_tdt, and asserts the round-trip (reader consulted, sink reached). See §6.
  • #4  config.ts exposes DEFAULT_WINDOW_CONFIG and DEFAULT_HDBSCAN_CONFIG and types.ts defines the shared stage types.
    Done = config.ts exports both defaults with the §5/§6 shapes; types.ts exports VisitRow, PageVector, DistanceMatrix, HdbscanRaw, RepresentedCluster exactly as in §3 above.
  • #5  A package README documents the module boundary and the dependency-injection contracts.
    Done = tdt/README.md explains: the wall (no vscode/src imports), the DuckDB single-writer rationale, the four ports and who supplies each, and the camelCase↔snake_case quarantine. Written canonically (present tense, system-as-it-is).

Scope discipline (constitution / YAGNI). 36.1 builds only the seams. No windowing, no embedding, no distance matrix, no fit call, no persistence schema, no MCP routes. Those are 36.2–36.9. The temptation to "stub in a little real logic" is surplus — the no-op orchestrator is intentionally empty of behavior.
