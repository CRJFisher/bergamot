Task 39.8 — Close the plaintext visit-inbox gap

Pre-build comprehension companion · privacy-overhaul branch

1. The gap

The problem in one sentence: Between HTTP accept and the DuckDB write, every visit is persisted as a plaintext JSON file at <storage_base>/visit_inbox/<id>.json. The file contains URL, referrer, title, and timestamps — the same data the encrypted DuckDB protects. The "front door" is unencrypted.

Current data flow on POST /visit:

→

URL · referrer · title · timestamps

After the DuckDB write succeeds, remove_visit deletes the file. But: the delete is not instantaneous, the file is forensically recoverable after deletion, and if the extension crashes mid-ingest the file stays indefinitely.

2. The fix — Option A: inbox table in the encrypted DuckDB

Chosen approach: Add a visit_inbox table inside the existing encrypted metadata DuckDB. Rows are inserted before returning 200; deleted once the capture pipeline commits the visit. No files on disk.

New data flow on POST /visit:

→

→

(same key as metadata store)

Restart recovery now reads the visit_inbox table instead of the directory. The property is preserved: visits written before a crash are re-enqueued on startup and processed exactly once (ids are content-hashed, insertion is idempotent).

Why Option A over Option B (encrypt the files)?

Option A: DuckDB tableOption B: Encrypt the files

3. New table schema

-- Added to create_metadata_schema() in duck_db.ts
CREATE TABLE IF NOT EXISTS visit_inbox (
  id             TEXT PRIMARY KEY,  -- md5(url:page_loaded_at) — same as visit.id
  url            TEXT NOT NULL,     -- for forget cascade selector matching
  page_loaded_at TEXT,              -- for time-range selector matching
  visit_json     TEXT NOT NULL      -- full JSON of ExtendedPageVisit for reload
)

The url and page_loaded_at columns exist only for the forget cascade — they let the cascade SELECT + DELETE without parsing JSON. The full visit rides in visit_json for the reload path.

4. Module dependency change

Pre-existing circular dependency (exists today, must be broken):
visit_inbox.ts imports ExtendedPageVisit, is_complete_visit from ./visit_queue_processor
visit_queue_processor.ts imports load_inbox, remove_visit from ./visit_inbox

After the change, visit_inbox.ts also needs to import DuckDB from ./duck_db. If we keep the types in visit_queue_processor.ts, the cycle gets worse. The fix: extract the shared types to a new module.

6. Async cascade

All inbox operations are now async. The key change is in VisitQueueProcessor.start():

// BEFORE
start(): void {
  this.reload_persisted_visits();   // sync
  this.start_orphan_retry_timer();
  this.schedule_batch_processing();
}

// AFTER
async start(): Promise {
  await this.reload_persisted_visits();   // async load from DB
  this.start_orphan_retry_timer();
  this.schedule_batch_processing();
}

The reload must complete before processing begins — firing-and-forgetting is not safe (the batch timer fires at 1 second; a slow DB load could miss it, but the correctness guarantee requires the reload to finish first).

setup_queue_processor() in server_manager.ts becomes async and awaits queue_processor.start().

7. Right-to-forget cascade change

The cascade currently calls sweep_visit_files(storage_base, selector) which sweeps both visit_inbox/ and captures/ directories. After this change:

  • visit_inbox/ is gone → add a DB table sweep instead
  • captures/ stays (dev replay ring — explicitly out of scope)
// IN right_to_forget.ts — new function:
async function sweep_visit_inbox(
  metadata_db: DuckDB,
  selector: ForgetSelector
): Promise {
  const rows = await metadata_db.query<{ id: string; url: string; page_loaded_at: string | null }>(
    `SELECT id, url, page_loaded_at FROM ${VISIT_INBOX_TABLE}`
  );
  const to_delete = rows.filter(r => selector_matches(selector, r.url, r.page_loaded_at));
  if (to_delete.length === 0) return 0;
  const { placeholders, params } = in_list(to_delete.map(r => r.id), "iid");
  await metadata_db.execute(
    `DELETE FROM ${VISIT_INBOX_TABLE} WHERE id IN (${placeholders})`,
    params
  );
  return to_delete.length;
}

This runs between the plaintext captures/ sweep and the content-cache sweep — preserving the cascade ordering (transient/derived before durable metadata).

Transaction note: The inbox sweep does NOT run inside forget_metadata's isolated transaction because isolated_transaction's callback only provides a no-return run function. The inbox DELETE runs on the main connection, immediately before the transaction — the same atomicity bound as the rest of the cross-store cascade (re-running is idempotent).

Risks and sharp edges
  • Double-enqueue on restart: persist_visit uses ON CONFLICT (id) DO NOTHING — a duplicate persist (e.g. if the `/visit` handler retries) is a no-op. The reload path is safe.
  • Partial ingest crash: If the extension crashes after the DB write but before remove_visit, the visit stays in visit_inbox. On restart, load_inbox re-enqueues it. The DuckDB insertion is idempotent (ON CONFLICT DO NOTHING), so re-processing is safe.
  • Malformed rows: load_inbox deletes rows whose visit_json fails is_complete_visit (same semantics as the file-based inbox). These are rows written by an older model; the delete-on-load is intentional.
  • Transaction scope: The inbox DELETE in the forget cascade runs on the main connection (not inside the isolated transaction), same as the content cache sweep. Cross-store atomicity is impossible; the ordering (inbox before metadata) keeps failures in the safe direction.
  • Dev replay ring: captures/ remains plaintext — this is documented as out of scope and confirmed by the task description. The forget cascade continues to sweep it.
