Three candidate surfaces — skill, webview, note-stub write-back

All three consume the one integration primitive over the cluster + 36.5 label-bundle tables — none touches DuckDB. They layer, they do not compete: a note-stub backbone, a skill that acts and drives the backbone, and a VS Code webview accessory.

The three candidates over one primitive

Surfaces layer; they are not mutually exclusive

This is the market-validated pattern: Smart Connections exposes one embedding store through three intent-shaped surfaces (Connections / Lookup / Graph); Smart Graph treats "the graph as a decision surface" rather than a queryable table. The 36.8 split mirrors it exactly — one primitive, multiple consumers.

① Note-stub write-back — the PKM-native backbone

backbone Note-stub write-back → bergamot.staging/ the SURFACE-node spine · the literal hero-loop deliverable

Topic clusters become agent-authored markdown stubs written only into a quarantined bergamot.staging/ directory, never canonical notes (constitution principle 8). The user promotes a stub by hand. It is the most PKM-native of the three, surfaced ambiently by the user's own file-watcher — and the careful piece, because it is the one surface that writes into PKM territory.

Anatomy of a staged stub

# bergamot.staging/2026-W25--local-graph-clustering.md (agent-authored, promote by hand) --- bergamot_agent_authored: true run_id: 7f3a…c12 # lineage; survives the forget sweep generated_at: 2026-06-22T08:03:11Z tags: [hdbscan, graph-clustering, embeddings] # ← keyphrases --- # Local graph clustering for topic detection ← headline_title (H1) Six pages over Jun 16–22 · scope: arxiv.org (3), github.com (2), distill.pub (1) ## Pages in this thread - [HDBSCAN: density-based clustering](https://…) ← exemplar, pinned <!-- bergamot:cite page_session_id=ps_91a url=https://… --> - [Hierarchical density estimates](https://…) <!-- bergamot:cite page_session_id=ps_44e url=https://… --> - … 4 more members, ranked by membership probability > One-line summary, drafted by the skill. Review and promote to make it yours.

Strengths

  • PKM-native by construction — output is a note in the user's own tool, surfaced by their own file-watcher; the literal hero-loop deliverable, not a proxy.
  • Constitutionally the cleanest write surface scoped to staging: principle 8 satisfied by design (append-only, agent-tagged, hand-promoted, canonical never mutated). The one write the inviolables bless.
  • Host-portable as a filesystem primitive — a markdown-file write couples to zero PKM API, so it is the universal write-back fallback for every Wave (Foam, Dendron, Logseq, TiddlyWiki, Emacs, Anytype, Memos).
  • Ambient visibility without the user asking; beats the pull-only skill on passive surfacing.
  • Validated externally: Nooscope queues output to a vault inbox, Note Companion lands suggestions in an Inbox folder — the same quarantine-then-promote review gate.

Weaknesses

  • Net-new, most-code surface of the three: no staging module, workspace discovery, renderer, promotion-detection, or staging cascade exists today.
  • Idempotency over unstable cluster identity is hard — run-local labels plus full recompute; without the (unbuilt) lifeline tracker a re-run can emit a second stub for the same project.
  • Promotion is lossy to detect: a moved/renamed stub is indistinguishable from a deleted one, risking resurrection of a discarded stub.
  • Right-to-forget gap: staged stubs are plaintext outside the encrypted stores, so the cascade needs a new filesystem sweep keyed on the citation comment.
  • Quarantine fragile: a staging dir inside a PKM/git repo risks commit or sync despite principle 6 — needs auto-gitignore.

② Claude skill / sub-agent over scripts — actionability + stub driver

actionability Claude skill — SKILL.md + thin scripts in-workflow layer · host-agnostic push · drives the backbone

A thin orchestrator over the integration primitive (the task-31.12 pattern) doing no DB access of its own. Scripts read ~/.bergamot/port.json and hit the /query/cluster* routes over the loopback relay, exactly as mcp_server_standalone.ts does today. SKILL.md frontmatter follows the proven weekly-interests template (name, description, scoped allowed-tools). Three scripts: fetch_recent_clusters, summarise_cluster, draft_note_stub — and summarise_cluster → draft_note_stub is the in-workflow path that seeds the backbone.

An in-context recall invocation, mid-draft

user: what have I been reading about graph clustering lately? → skill: fetch_recent_clusters(from=last 7d) · GET /query/clusters → 100-row cap (MAX_QUERY_LIMIT) · live run only (status='complete') assistant: You have one active thread this week: ▸ Local graph clustering for topic detection (6 pages · coherence 0.71) scope: arxiv.org (3), github.com (2), distill.pub (1) exemplar: HDBSCAN: density-based clustering — https://… members: 6 pages ranked by membership probability Want me to draft a Map-of-Content stub for it? → draft_note_stub (writes to bergamot.staging/ only — you promote it by hand)

Strengths

  • Matches Bergamot's preferred integration pattern exactly: a thin SKILL.md + scripts over a single read primitive — the model specified in task-31.12 and proven by weekly-interests.
  • Host-agnostic by construction — needs only port.json + HTTP, so it runs against the future standalone daemon identically to today's extension backend; no VS-Code coupling.
  • Strongest in-workflow actionability: injects clusters + live member URLs into the active task where the user is already writing, and can act (draft a stub) in the same breath.
  • The natural DRIVER of the note-stub backbone — one skill both answers in-context and writes the staged stubs.
  • Cheapest surface; the only write is append-only into the quarantined staging dir, fully within principle 8.

Weaknesses

  • Weak passive/ambient visibility — it is pull, not push. It does not satisfy the constitution's habit-anchor "opens on launch / weekly notification" on its own; a scheduled routine only partially mitigates.
  • Depends on the primitive that does not exist yet — it cannot ship before cluster_reads.ts + the /query/cluster* routes are built.
  • draft_note_stub is the net-new, careful piece — append-only + agent-tagging + promote-by-hand is the real cost, not the skill wiring.
  • Cluster identity dangles across recomputes (run_id supersedes), so the skill must resolve clusters by current window each invocation, never a cached id.

Role in the recommended layering

The actionability layer, and it DRIVES stub generation — summarise_cluster → draft_note_stub seeds the backbone. It is also where the required user controls live: when the user renames a cluster, hides one, or marks a site as never-to-be-clustered, the skill writes that to a small Bergamot-owned table. Because the skill runs on every host, these day-one-required controls work everywhere — they don't depend on the VS Code webview being built.

③ VS Code webview — optional rich-visibility accessory

optional accessory VS Code webview — cluster cards + timeline richest visibility · VS-Code host only · NOT launch-blocking

A net-new WebviewView/Panel from the extension host — none exists today (current UI is a TreeDataProvider + HoverProvider only). The webview never touches DuckDB: the extension host reads port.json, fetches the /query/cluster* routes with the per-extension capability token, and postMessages results to a sandboxed CSP/nonce webview that renders timeline + cards client-side. It is the literal example of the constitution's named push surface — "a VS Code panel that opens on launch."

Strengths

  • Directly satisfies the constitution's named push-surface — "a VS Code panel that opens on launch" is the literal example. The strongest ambient-visibility candidate inside VS Code: clusters are SEEN without asking.
  • Richest home for the control surface — visual cards make suppress / rename / never-cluster-origin discoverable and one-click; curation writes go to Bergamot's own tables, constitutionally clean.
  • Consumes the primitive cleanly with an in-repo template (port.json discovery + token-authed fetch); the panel never opens DuckDB, preserving single-writer ownership.
  • Excellent privacy posture — client-side render over loopback fetches of derived metadata + labels only; no new store, no egress, no PKM writes.
  • Best fit for timeline / weekly-review / dormant-thread workflows where spatial layout beats a text-only answer.

Weaknesses

  • Host lock-in is the central tension — VS-Code-host-specific UI, serves only Wave 1 (Foam/Dendron). It re-localizes visibility into one host, opposing the portability vision the same task is built around.
  • Highest build AND maintenance cost: net-new HTML/CSS/JS bundle, a build step, CSP/nonce handling, a message-passing protocol, theming, and ongoing VS Code API churn.
  • Does not port to the daemon future — a VS-Code-coupled dashboard is non-transferable; other hosts fall back to the skill/stub layers.
  • Weak in-workflow actionability relative to the skill — it surfaces and curates but does not draft stubs or answer in-context-while-writing queries.
  • Ambient visibility is gated on the user living in VS Code; for Obsidian/Logseq users the "opens on launch" anchor never fires.

How they layer — the recommendation

backbone Note-stub write-back

The SURFACE-node spine: a markdown note in the user's own tool, surfaced ambiently. The universal fallback that ports to every PKM host.

actionability Claude skill

The in-workflow layer that also DRIVES the backbone. The host-agnostic push vehicle (on-demand + scheduled weekly digest). Cheapest surface.

user controls (required) The skill, writing to a control table

The user must be able to fix the clusters they're shown: rename a mislabeled one, hide one they don't want, and mark a site as "never cluster this origin." The constitution requires these to ship on day one — clustering without them is surveillance, not a feature. The skill records each action by writing to one small Bergamot-owned table, so the controls work on every host. They are NOT built only into the webview, which would strand non-VS-Code users.

optional accessory VS Code webview

A rich-visibility accessory for the VS Code host only. Off the launch critical path; build after the backbone + skill prove the loop.

The recommendation

Backbone = note-stub write-back into bergamot.staging/ (most PKM-native, universal fallback). Actionability layer = the Claude skill, which also drives stub generation. Required user controls = rename / hide / never-cluster-a-site, recorded by the skill into a Bergamot-owned table so they work on every host — never built only into the webview. Optional accessory = the VS Code webview, for VS Code users only, after the loop is proven. This satisfies AC#2 ("every surface consumes one primitive") and the constitution's push-surface mandate without betting the hero loop — or the required day-one controls — on the one host-locked, most-expensive surface.
