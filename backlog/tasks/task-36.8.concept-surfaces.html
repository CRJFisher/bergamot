Three cluster surfaces — skill, webview, note-stub write-back

All three consume the one integration primitive over the cluster + 36.5 label-bundle tables — none touches DuckDB. They layer, they do not compete: a note-stub backbone and a skill that acts and drives it both ship in v1; the VS Code webview is the one deferred accessory.

The three candidates over one primitive

Surfaces layer; they are not mutually exclusive

This is the market-validated pattern: Smart Connections exposes one embedding store through three intent-shaped surfaces (Connections / Lookup / Graph); Smart Graph treats "the graph as a decision surface" rather than a queryable table. The 36.8 split mirrors it exactly — one primitive, multiple consumers.

① Note-stub write-back — the PKM-native backbone

backbone Note-stub write-back → bergamot.staging/ the SURFACE-node spine · the hero-loop deliverable shipped

Topic clusters become agent-authored markdown stubs written only into a quarantined bergamot.staging/ directory, never canonical notes (constitution principle 8). The user promotes a stub by hand. It is the most PKM-native of the three, surfaced ambiently by the user's own file-watcher — and the careful piece, because it is the one surface that writes into PKM territory. The renderer (note_stub.ts) is pure; the writer (staging_writer.ts) owns every filesystem effect.

Anatomy of a staged stub

# bergamot.staging/2026-W25--local-graph-clustering.md (agent-authored, promote by hand) --- bergamot_agent_authored: true run_id: 7f3a…c12 generated_at: 2026-06-22T08:03:11Z lineage_key: 2026-W25--local-graph-clustering # ISO-week + slug(label) fingerprint: a91c… # content gate: skip an unchanged rewrite window_start: 2026-06-16T… # read by the time-range forget sweep window_end: 2026-06-22T… tags: - hdbscan - graph-clustering # ← keyphrases --- # Local graph clustering for topic detection ← headline_title (H1) Scope: arxiv.org, github.com +1 site · 2026-06-16 → 2026-06-22 ← scope verbatim > 6 pages cohered around Local graph clustering … Review and promote to make it yours. ## Pages in this thread - [HDBSCAN: density-based clustering](https://…) (exemplar, pinned) <!-- bergamot:cite page_session_id=ps_91a url=https%3A%2F%2F… --> - [Hierarchical density estimates](https://…) <!-- bergamot:cite page_session_id=ps_44e url=https%3A%2F%2F… --> - … 4 more members, ranked by membership probability

Strengths

  • PKM-native by construction — output is a note in the user's own tool, surfaced by their own file-watcher; the literal hero-loop deliverable, not a proxy.
  • Constitutionally the cleanest write surface scoped to staging: principle 8 satisfied by design (append-only at the canonical boundary, agent-tagged, hand-promoted, canonical never mutated).
  • Host-portable as a filesystem primitive — a markdown-file write couples to zero PKM API, so it is the universal write-back fallback for every Wave (Foam, Dendron, Logseq, TiddlyWiki, Emacs, Anytype, Memos).
  • Ambient visibility without the user asking; beats the pull-only skill on passive surfacing.
  • Validated externally: Nooscope queues output to a vault inbox, Note Companion lands suggestions in an Inbox folder — the same quarantine-then-promote review gate.

Residuals (the cost, now paid)

  • The most-code surface of the three: a staging module, workspace discovery, renderer, ledger-based promotion-safety, and a forget sweep — all now shipped in note_stub.ts / staging_writer.ts / staging_root.ts.
  • Cluster identity is per-run, so the filename keys on a stable lineage (ISO-week + label slug). Until lifeline_id lands, a same-week label change can spawn a second stub; the fingerprint gate and ledger bound the churn.
  • Promotion is inferred from the filesystem: a .bergamot-ledger.json records every emitted lineage so a promoted-out file is never recreated and a user-owned file (absent from the ledger) is never clobbered.
  • Staged stubs are plaintext outside the encrypted stores, so the forget cascade includes a filesystem sweep matching on the citation comment.
  • A staging dir inside a PKM/git repo risks commit or sync — defended by an auto-written .gitignore (*).

② The bergamot-clusters skill — actionability + stub driver

actionability bergamot-clusters skill — SKILL.md + a Node dispatcher in-workflow layer · host-agnostic push · drives the backbone shipped

A thin orchestrator over the integration primitive doing no DB access of its own. It lives at skills/bergamot-clusters/ as tracked source, symlinked into .claude/skills/ (which is gitignored). A single dependency-free Node dispatcher reads ~/.bergamot/port.json and hits the /query/cluster* routes over the loopback relay; subcommands cover the whole surface: recent, page, cluster, coverage, stub, suppress, rename, block (and their inverses). The cluster → stub path is the in-workflow loop that seeds the backbone by POSTing to /stage_cluster.

An in-context recall invocation, mid-draft

user: what have I been reading about graph clustering lately? → skill: node bergamot_clusters.js recent --days 7 · GET /query/clusters → 100-row cap (MAX_QUERY_LIMIT) · live run only (status='complete') assistant: You have one active thread this week: ▸ Local graph clustering for topic detection (6 pages · coherence 0.71) scope: arxiv.org, github.com +1 site exemplar: HDBSCAN: density-based clustering — https://… members: 6 pages ranked by membership probability Want me to draft a Map-of-Content stub for it? → cluster --id … then stub --id … (stub POSTs /stage_cluster → bergamot.staging/ only — you promote it by hand)

Strengths

  • Matches Bergamot's preferred integration pattern exactly: a thin SKILL.md + a dispatcher over a single read primitive — the model proven by weekly-interests.
  • Host-agnostic by construction — needs only port.json + HTTP, so it runs against the future standalone daemon identically to today's extension backend; no VS-Code coupling.
  • Strongest in-workflow actionability: injects clusters + live member URLs into the active task where the user is already writing, and can act (draft a stub, curate a cluster) in the same breath.
  • The DRIVER of the note-stub backbone and the host-agnostic home of the launch-blocking controls — one skill answers in-context, writes staged stubs, and records suppress/rename/block.
  • Dependency-free and cheapest surface; the only writes are append-only staged stubs and curation rows.

Residuals

  • Weak passive/ambient visibility — it is pull, not push. The constitution's habit-anchor "opens on launch / weekly notification" is met by a scheduled digest routine, not by the skill on its own.
  • Cluster ids dangle across recomputes, so every command resolves a cluster by a fresh id in the same turn, never a cached one — a discipline the SKILL.md spells out.
  • If the extension is not open, the loopback routes are down; the script reports "Bergamot server not running" and asks the user to open it.

Role in the shipped layering

The actionability layer, and it DRIVES stub generation — the stub command POSTs to /stage_cluster to seed the backbone. It is also where the launch-blocking controls live: suppress / rename / block POST to the control route. Because the skill runs on every host, these day-one controls work everywhere — they do not depend on the VS Code webview being built. The weekly digest is a /schedule routine that runs recent + coverage and summarises.

③ VS Code webview — the one deferred accessory (36.8.8)

accessory VS Code webview — cluster cards + timeline richest visibility · VS-Code host only · NOT launch-blocking deferred · 36.8.8

The one surface NOT in v1. It would be a net-new WebviewView/Panel from the extension host (current UI is a TreeDataProvider + HoverProvider only). The webview would never touch DuckDB: the extension host reads port.json, fetches the /query/cluster* routes with the per-extension capability token, and postMessages results to a sandboxed CSP/nonce webview that renders timeline + cards client-side. It is the literal example of the constitution's named push surface — "a VS Code panel that opens on launch" — but host-locked, highest-cost, and explicitly off the launch critical path, so it lands as a post-launch accessory.

Strengths

  • Directly satisfies the constitution's named push-surface — "a VS Code panel that opens on launch" is the literal example. The strongest ambient-visibility candidate inside VS Code: clusters are SEEN without asking.
  • Richest home for the control surface — visual cards make suppress / rename / never-cluster-origin discoverable and one-click; curation writes go to Bergamot's own tables, constitutionally clean.
  • Consumes the primitive cleanly with port.json discovery + token-authed fetch; the panel never opens DuckDB, preserving single-writer ownership.
  • Excellent privacy posture — client-side render over loopback fetches of derived metadata + labels only; no new store, no egress, no PKM writes.
  • Best fit for timeline / weekly-review / dormant-thread workflows where spatial layout beats a text-only answer.

Weaknesses — why it is deferred

  • Host lock-in is the central tension — VS-Code-host-specific UI, serves only Wave 1 (Foam/Dendron). It re-localizes visibility into one host, opposing the portability vision the same task is built around.
  • Highest build AND maintenance cost: net-new HTML/CSS/JS bundle, a build step, CSP/nonce handling, a message-passing protocol, theming, and ongoing VS Code API churn.
  • Does not port to the daemon future — a VS-Code-coupled dashboard is non-transferable; other hosts fall back to the skill/stub layers.
  • Weak in-workflow actionability relative to the skill — it surfaces and curates but does not draft stubs or answer in-context-while-writing queries.
  • Ambient visibility is gated on the user living in VS Code; for Obsidian/Logseq users the "opens on launch" anchor never fires.

How they layer — the shipped surface

backbone · built Note-stub write-back

The SURFACE-node spine: a markdown note in the user's own tool, surfaced ambiently. The universal fallback that ports to every PKM host.

actionability · built bergamot-clusters skill

The in-workflow layer that also DRIVES the backbone. The host-agnostic push vehicle (on-demand + scheduled weekly digest). Cheapest surface.

user controls · launch-blocking · built The skill, writing to a control table

The user fixes the clusters they're shown: rename a mislabeled one, hide one they don't want, and mark a site as "never cluster this origin." The skill records each action by writing to topic_cluster_control, so the controls work on every host. They are NOT built only into the webview, which would strand non-VS-Code users.

accessory · deferred (36.8.8) VS Code webview

A rich-visibility accessory for the VS Code host only. Off the launch critical path; built after the backbone + skill prove the loop. The one piece deferred past v1.

The shipped surface

Backbone = note-stub write-back into bergamot.staging/ (most PKM-native, universal fallback). Actionability layer = the bergamot-clusters skill, which also drives stub generation. Launch-blocking controls = rename / hide / never-cluster-a-site, recorded by the skill into topic_cluster_control so they work on every host — never built only into the webview. Deferred accessory = the VS Code webview, for VS Code users only, built after the loop is proven. This satisfies the contract goal ("every surface consumes one primitive") and the constitution's push-surface mandate without betting the hero loop — or the day-one controls — on the one host-locked, most-expensive surface.
