Page vectorisation — one definition, one embed pass ahead of TDT

Page vectorisation turns one re-downloaded public page into one L2-normalized vector — the unit clustering consumes. Task 36.3 splits in two: the pure library defines the representation, math, and guards; the store + batched embedder (36.3.1) adds a DuckDB store and a batched embed pass that vectorises the cached corpus ahead of a clustering run.

The split, in one line

36.3 owns the definition of the page vector (what it is, how it is built, what is excluded); 36.3.1 owns where it lives and what produces it — a DuckDB store, a batched embed pass ahead of TDT, and the forget cascade. The capture path does no embedding; TDT and RAG only ever read the result.

Decisions already banked across the pair

DecisionResolutionWhere
Where do page vectors live?Encrypted DuckDB store via the VectorStore port — LanceDB evaluated and rejected (cannot encrypt at rest while searchable; content-derived vectors are sensitive)36.3 / 36.3.1
When does embedding happen?A batched embed pass ahead of a clustering run — not per-page at ingestion; the capture path does no embedding; downstream only reads36.3.1
How is the embed kept off the event loop?The batched pass runs on a worker; the model loads once per pass and is released after — resident only while a pass runs36.3.1
What relaxes the determinism requirement?Build-once-and-read means clustering is reproducible by reading fixed bytes; bitwise embedder identity is not load-bearing, only best-effort single-thread on the miss path36.3.1
Which embedding model?bge-small-en-v1.5 ONNX q8, 384d, via @huggingface/transformers fully offline, no instruction prefix; gte-small fallback36.3.1
How is the cache invalidated?embedding_model_id folds model + quant + dim + repr-rule version; any change is a new key, a clean miss the next pass rebuilds36.3 / 36.3.1
Is similarity search included?No — deferred to RAG (task-31), which shares the same encrypted store and embedding space; TDT needs only get/put36.3
Why one vector per page

Clustering operates at project altitude (page-sets), not paragraph altitude, and the ~5k dense-matrix ceiling makes the page the right unit (n = page count, a cluster = a set of pages). A whole-page embedding is coarse by design — which is exactly why the dispersion guard inside build_page_vector exists.
