Persistence: cluster tables, run keying, idempotency

Step 6 writes clustering output to four DuckDB tables, written ONLY by the extension's single writer. A run is identified by a run_id hash; re-running it decides no-op / atomic replace / create + supersede inside one transaction.

The work splits across a seam — @bergamot/tdt hashes and assembles records (pure, no DB); vscode/ reads-decides-writes them (transactional). Noise persists as explicit member rows so coverage is derivable from the cluster tables alone.

The one sentence

@bergamot/tdt stays pure: run_keying.ts derives run_id + input_fingerprint, and assemble_run_bundle() turns clustering output into { run, clusters, members } rows (one member row per page, noise included).

The extension's ClusterStore.persist takes that bundle and, in one transaction, reads the existing run by id and decides no-op / atomic-replace / create — superseding any other live run for the window on both the replace and create paths, so exactly one complete run survives.

The idempotency state machine — the crux

The two keys — run_id identifies the run, input_fingerprint detects data drift

Two distinct hashes answer two distinct questions. run_id answers "is this the same logical run?" — it is the row's identity. input_fingerprint answers "did the data inside the same logical run change?" — it is read only when a row with that run_id already exists.

run_id — the run's IDENTITY (PK)

sha256 of the canonicalized natural key

run_id = sha256( canonical( window_start · window_end · params_hash · embedding_model_id · algo_version ) )

Canonicalized so two logically-identical runs hash identically: window bounds normalized to one ISO form (canonical_timestamp), sorted-key params_json, shortest round-trip floats. A change here yields a NEW key — a different row that creates and supersedes the prior window run:

  • window bounds — the ACTUAL bounds used, including subdivision; stored in the same canonical form they are hashed in
  • params_hash — HDBSCAN config + pooling + windowing policy + matryoshka dim (none visible in other columns)
  • embedding_model_id — model + dim + page-representation rule version
  • algo_version — bumps on clustering-tfjs BACKEND change, not just code
input_fingerprint — the DATA inside the run

sha256 of the sorted actual inputs

input_fingerprint = sha256( sorted (page_session_id, embedding_vector_version) )

Same run_id, different fingerprint means the inputs shifted under a fixed key. A change here triggers an atomic-replace, not a new run. It catches the two ways a closed window's data can move:

  • re-embedding — a page's embedding_vector_version changed (sourced from topic_page_vector.built_at, rewritten on every re-embed), so the vector fed to HDBSCAN is different
  • a late-arriving visit — capture is async and referrer chains backfill, so a visit whose page_loaded_at lands in an already-closed window adds a page_session_id
Why canonicalize the window bounds, and why two keys not one

Bounds are normalized to one ISO form both where run_id is hashed and where the row is stored, so the supersede equality predicate can't miss the prior run on format drift. Keeping inputs OUT of run_id lets a late visit refresh the window in place rather than spawn a brand-new run.

The four tables — soft references, not foreign keys

Noise = a member row, never a cluster row, never a NULL-sentinel

A −1 page gets a topic_cluster_member row with is_noise = TRUE and cluster_id = NULL — but the coverage query reads the is_noise flag, not the NULL cluster_id. Persisting noise (not omitting it) makes coverage derivable from the cluster tables alone, with no re-join and no "noise" vs "not yet processed" confusion.

assemble → persist — how clustering output becomes rows

The same six-page window from 36.5 (one React cluster, one Hacker News noise page) assembled into rows: one topic_cluster row for label 0, and six topic_cluster_member rows — one per page, the noise page included.

tdt/src/persist.ts  ·  pure assembly — no DB, deterministic (created_at injected), returns the bundle the sink persists
// Pure: clustering output → records. No DuckDB, no transaction, no clock — that
// is the extension's job. One member row PER PAGE, noise included, so coverage
// is derivable from the member rows alone (plan §8).
export function assemble_run_bundle(args: AssembleArgs): RunBundle {
  // run_id keys off canonicalized window bounds, and the row stores THAT form,
  // so the supersede equality predicate can't miss on ISO-format drift.
  const window_start = canonical_timestamp(args.window_start);
  const window_end = canonical_timestamp(args.window_end);
  const run_id = compute_run_id({ window_start, window_end, params_hash, embedding_model_id, algo_version });
  const input_fingerprint = compute_input_fingerprint(...);   // sorted (page_session_id, vector_version)

  const members: MemberRecord[] = args.visits.map((v, i) => {
    const is_noise = args.raw.labels[i] < 0;                  // HDBSCAN −1
    return {
      run_id, page_session_id: v.page_session_id,
      cluster_id: is_noise ? null : cluster_id_by_label.get(args.raw.labels[i]),   // set iff !is_noise
      is_noise, probability: is_noise ? 0 : args.raw.probabilities[i],
      page_loaded_at: v.page_loaded_at,                       // denormalized for time filters
      is_exemplar: exemplar_rows.has(i),                    // step-5 representative_index
    };
  });
  // run.status = 'complete' written directly; 'running'/'failed' are a 36.9 seam.
  return { run, clusters, members };
}

The coverage query — clustered / total, from the cluster tables alone

cluster_store.ts · coverage()  ·  clustered / total over one run's member rows · no re-join to capture tables
-- AC #4: per-window coverage from topic_cluster_member alone.
-- is_noise (not a NULL cluster_id) is the signal, so the math is NULL-free.
SELECT
  count(*)                                  AS total,
  count(*) FILTER (WHERE NOT is_noise) AS clustered,
  count(*) FILTER (WHERE is_noise)     AS noise
FROM topic_cluster_member
WHERE run_id = $run_id;   -- coverage = clustered / total in JS; null when total = 0
-- for the six-page window above: 5 / 6 = 0.833
Why noise must be persisted for this to work

If noise pages were omitted, total would only count clustered pages and coverage would always read 1.0 — meaningless. Persisting one member row per page, noise flagged, makes the denominator the true window size. The run row also caches cluster_count and noise_count for a row-free read, but the member-row query is the authoritative, re-derivable source.

The cluster tables join the right-to-forget cascade

1

The cascade is a single home — every derived store joins it as it lands

vscode/src/right_to_forget.ts deletes the metadata tables, the topic_page_vector cache (36.3.1), the TDT cluster memberships (this task), and the encrypted content cache. This slice deletes a forgotten page's cluster membership inside the same dedicated-connection metadata transaction.

vscode/src/right_to_forget.ts · forget_metadata · parent AC #7
2

It deletes topic_cluster_member rows only — never the topic_cluster / topic_run rows

A forget resolves a selector to a set of page_session_ids and deletes their topic_cluster_member rows in the same transaction as the metadata they derive from. Clusters and runs are left for the next run to re-key and atomically replace — a bounded, non-reconstructable residual.

DELETE FROM topic_cluster_member WHERE page_session_id IN (...) · same isolated_transaction
3

Why members, not clusters — the per-page vector is reconstructable, the aggregate is not

The per-page embedding (topic_page_vector) is the reconstructable artifact and is deleted. A cluster's frozen representative_vector is an irreversible aggregate and a run is window-level provenance, so they stay until the next clustering pass re-keys the window (its input_fingerprint changes) and replaces them — the same isolated_transaction primitive persist uses.

Acceptance criteria — and how each was met

Net effect

A clustering run is now durable, reproducible, and idempotent: an unchanged window costs nothing, a re-embed or late visit refreshes it atomically, and a model/params/algo change creates a new run while superseding the prior one — history retained, exactly one live run per window.

The pure library owns identity and assembly; the extension owns the one race-free read-decide-write. Next, 36.7 adds the validation score, and 36.9 wires the trigger that calls persist off the event loop (and where 'running'/'failed' become live).
