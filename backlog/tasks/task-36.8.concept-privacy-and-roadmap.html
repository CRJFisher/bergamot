Privacy guarantees & the decomposition into sub-tasks

The constitution forces a read/write asymmetry on every cluster surface. That asymmetry resolves the read-only-vs-read-write question, and the resolution decomposes into nine follow-on implementation sub-tasks — each justified against the UNDERSTAND / SURFACE spine.

The read/write asymmetry every surface respects

Principle 8 — staging only, never canonical notes

Constitution principle 8 — inviolable (relaxable only by user amendment)
"Autonomous agents never write to canonical PKM notes. Agents write append-only to a quarantined staging area the user promotes by hand. Agent-authored content is clearly tagged. The deterministic source of truth is never mutated by an agent."

docs/constitution.md:90 · governs the canonical-note boundary

The external landscape validates the staging quarantine

Nooscope queues AI output in SQLite then flushes to a vault inbox, "maintaining a human review gate before permanent integration"; Note Companion lands suggestions in a dedicated Inbox folder. bergamot.staging/ is the same quarantine pattern — its "human review gate" / "preserve intentionality" rationale is reusable language for the ADR (sub-task 9).

Metadata / encrypted-store invariants every surface must respect

#InvariantWhat it forces on a surface
1 The metadata store is the durable source of truth and the syncable artifact (principle 6). Surfaces read derived metadata only; they never become a second source of truth or an un-forgettable copy.
2 Re-downloaded content lives in a separate quarantined, encrypted, scoped, deletable tier — never git-tracked, never the PKM repo. Two stores, two OS-keystore-backed DEKs (encryption_key.ts: METADATA_DB_KEY_SECRET / CONTENT_CACHE_KEY_SECRET); a surface never co-mingles them.
3 Staging is the privacy seam in write-back: staged stubs are plaintext markdown where the file-watcher sees them. Defense is quarantine-by-directory + never-canonical + auto-gitignore, not encryption — a staging dir inside a PKM/git repo risks commit or sync despite principle 6 and must be auto-gitignored.
4 Right-to-forget cascades (principle 4): forgetting by URL / origin / time-range deletes cluster memberships, vectors, AND derived staged stubs + curation state. Staged stubs are plaintext outside the encrypted stores, so the cascade needs a new filesystem sweep matching on the per-link citation key (sub-task 3), ordered and idempotent like the existing cascade.
Reads are clean by the privacy core's own design

The clusterable corpus is the re-downloadable public subset by design: auth-walled / dead pages are excluded from clusters, so a surface never risks exposing login-walled content. Reads are loopback-bound, per-extension capability-token authed (principle 7), over metadata-only tables — no page content, no re-download triggered by a surface.

The explicit read-only vs read-write decision (AC#4)

DirectionModeWhat is writtenConstraint
Toward the PKM read-mostly The note-stub only — write-only into bergamot.staging/. Append-only at the canonical boundary (per-file overwrite of un-promoted drafts permitted). No reading PKM edits back as signal — a rename is not an approval; that feedback loop is explicitly out of scope.
Toward Bergamot's own state read-write Cluster-boundary curation — suppress / rename / never-cluster-origin. Writes to a new DuckDB control table in the encrypted metadata store. In scope now, launch-blocking (constitution §3), keyed to survive run_id recomputes, and itself a right-to-forget cascade target.
The brittle trap to never conflate

Curation is a write-back control signal that ships now; PKM-edit-derived feedback is explicitly out of scope. The two must not be conflated — treating stub edits as curation would skirt the principle-8 boundary and is brittle (a rename is not an approve). Stubs flow out to staging; nothing flows back from PKM edits.

Decomposition — the follow-on implementation sub-tasks

Nine sub-tasks, each justified against the intention tree: UNDERSTAND (turn browsing into a queryable knowledge base) and SURFACE (push the projects the user is actually working on at a habit anchor). The integration primitive is the blocking dependency for everything.

Sequence 0 — blocking dependency (must ship first)
01 depends-on: nothing read-only

Implement the cluster read primitive (cluster_reads.ts)

Four pure (db, params) → JSON functions filtered to status='complete' live runs: list_clusters_in_range, get_cluster, list_clusters_for_page, window_coverage. Return the label-bundle fields exactly (headline_title, scope with pinned JSON shape, keyphrases, display_label, representation_version), size, coherence, time_span; for members join url/title/page_loaded_at/probability/is_exemplar. Exclude representative_vector. list_clusters_for_page returns page_status ∈ {clustered, noise, unseen} distinguishing processed-noise (is_noise = true) from never-clustered. Clamp via MAX_QUERY_LIMIT. Colocated cluster_reads.test.ts with __fixtures__/.

UNDERSTAND: the one queryable contract over the knowledge base; every surface and the whole SURFACE spine depend on it.

02 depends-on: 01 read-only

Bind to four /query/cluster* routes + retire old scope, preserving visits_in_window

Add GET /query/clusters, /query/cluster, /query/clusters_for_page, /query/cluster_coverage mirroring the existing /query/* pattern (param validation, 400, MAX_QUERY_LIMIT clamp, res.json). Explicitly NOT /query/topic_* and NO new MCP ListTools/CallTool cases. Rewrite plan §9 to describe this primitive and delete its retired three-tool/route spec — while explicitly preserving the GET /query/visits_in_window?from=&to= Stage-1 bulk read (does not exist in server_manager.ts today; belongs to the clustering pipeline's input path, not the retired surface). Add cluster tables to the right-to-forget cascade.

AC#2 + principle 12: retires the DB-shaped raw-tool scope cleanly with no half-built routes or stale canonical doc, without orphaning Stage-1.

Sequence 1 — backbone + actionability (the hero loop)
03 depends-on: 01 read-write → staging

Note-stub renderer + staging writer (the backbone)

Render one markdown stub per cluster (display_label/headline_title → H1, keyphrases → tags, member URLs → MoC links, exemplar pinned, one-line summary) into bergamot.staging/ via pure filesystem write with workspace discovery, agent-tagged frontmatter (run_id, generated-at), auto-gitignore. Pin the per-link citation format here: each member link embeds page_session_id + URL in a machine-matchable form so the right-to-forget filesystem sweep can reliably match and delete stubs citing a forgotten URL/origin.

SURFACE: the literal hero-loop deliverable, the PKM-native push surface, satisfying principle 8 by construction; the citation key is the contract the forget sweep matches on.

04 depends-on: 03 read-write → staging

Staging idempotency + re-run/promotion behavior + forget sweep

Deterministic filename per lineage (lifeline_id when present — currently NULL, a Phase-4 seam, types.ts:70 — else run_id + local label). Re-run overwrites un-promoted stubs in place (permitted: rewrites the agent's own un-promoted draft, never a canonical note); never re-create a stub moved/promoted out, never resurrect a discarded one. Gate restaging to a changed fingerprint. Implement the right-to-forget filesystem sweep matching the sub-task-3 citation key, ordered and idempotent like the existing cascade.

SURFACE (trust + principle 4): without idempotency, unstable run-local labels emit churning stubs and erode the hero loop's trust; without the keyed sweep, plaintext stubs escape the forget cascade.

05 depends-on: 02, 03, 07 read drives writes

Build the Bergamot cluster skill (SKILL.md + scripts)

Author SKILL.md (frontmatter + scoped allowed-tools per the weekly-interests template) and fetch_recent_clusters + summarise_cluster + draft_note_stub scripts that call the primitive only, plus the curation actions (suppress / rename / never-cluster-origin) that POST to the control route (sub-task 7). The skill answers in-context recall, DRIVES stub generation (summarise_cluster → draft_note_stub), and is the host-agnostic driver for the launch-blocking control surface. Resolve clusters by current window each invocation (cluster ids dangle across recomputes).

SURFACE + UNDERSTAND: the in-workflow actionability layer, the host-agnostic push vehicle, and the host-agnostic home for the launch-blocking control surface; cheapest surface, the task-31.12 pattern.

06 depends-on: 05 read opt-in staging write

Schedule the cluster digest (weekly cron/routine)

Wire the skill to run on a documented weekly cadence, parameterised by window, emitting a digest artifact + optional desktop notification, and a staged weekly-review stub.

SURFACE (constitution.md:127): the host-agnostic push anchor — the pull-only mitigation — for hosts without a webview. Pull-first with opt-in weekly write to staging, per the notification-fatigue lesson: triaged, not a firehose.

Sequence 2 — mandatory control state + optional accessory
07 depends-on: 01 launch-blocking read-write → control

Cluster-control table + write route (host-agnostic)

New DuckDB control table (in the encrypted metadata store) + write endpoint for suppress / rename / never-cluster-this-origin, consumed by the skill (sub-task 5) so the launch-blocking control surface is host-agnostic and never gated on the webview. Suppression persists across recomputes keyed on stable identity; never-cluster-origin feeds the capture/skip-re-download list; the control state is a right-to-forget cascade target.

SURFACE (constitution.md:128, launch-blocking): converts "surveilled" into "seen"; mandatory, not optional. Ships with the skill on the launch path.

08 depends-on: 02, 07 optional · VS-Code host only

VS Code webview cluster dashboard (NOT launch-blocking)

Net-new WebviewView/Panel: timeline + cluster cards + member drill-down + domain scope, consuming the primitive via port.json + token-authed fetch in the extension host, postMessage to a sandboxed CSP/nonce webview; viewsContainers + a bergamot.openClusters command + opens-on-launch activation. Optionally hosts the control affordances from (7) as one-click card buttons — a richer host for them, never their only route.

SURFACE (constitution.md:127 for VS Code users): the richest ambient-visibility accessory and a discoverable control host, but explicitly host-locked and off the launch critical path — build after the backbone + skill + control route prove the loop; resist any PKM-write affordance.

09 depends-on: 03, 07 ADR · record

ADR for the read/write boundary (AC#4)

Record: stub write-back is write-only toward bergamot.staging/ (append-only at the canonical-note boundary, per-file overwrite of un-promoted drafts permitted) and feeds no signal back from PKM edits; cluster-boundary curation is a separate mandatory control surface over Bergamot's own tables (in scope now, launch-blocking, host-agnostic via the skill + control route), not inferred from promotion. Document the asymmetry, the "append-only governs the canonical boundary" reading of principle 8, and quote the Nooscope / Note Companion "human review gate" rationale.

principle 12: the canonical record downstream surfaces are built against.

Sequencing & dependencies at a glance

The decomposition in one line

One read primitive, then a PKM-native staging backbone driven by a host-agnostic skill, then a launch-blocking control surface that ships with the skill — with the VS Code webview as an optional accessory and an ADR recording the read/write asymmetry. Every sub-task traces to UNDERSTAND or SURFACE, and no surplus surface is built (YAGNI): representative_vector stays hidden, raw /query/topic_* tools are never re-created, and PKM-edit feedback is out of scope.
