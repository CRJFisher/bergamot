Task-40: Per-extension capability token
Constitution principle 7 — local server authentication

What this doc covers: the three-way design decision (browser pairing, MCP auth, token lifecycle), the full pairing sequence, honest limits of the defense, and how each file changes.

Why this exists

The local Express server is loopback-bound and CORS-filtered, but CORS is not authentication. Any process running as the user can POST to /visit (injecting fake browsing history) or GET from /query/capture_content (reading re-downloaded page text). Constitution principle 7 names a per-extension capability token as the required fix. This task ships that token.

Acceptance criteria

AC1 — /visit, /query/*, /dev_signal: rejected without token; succeed with it — server tests cover this.
AC2 — Token generated on first run, persisted in SecretStorage, delivered to browser via explicit pairing step. Mechanism + honest limits documented.
AC3 — MCP standalone authenticates without weakening the scheme. Token NOT in a world-readable file.
AC4 — CORS stays; loopback stays; neither is treated as authentication.
AC5 — docs/threat-model.md adversary B section reflects the shipped mechanism instead of "largest open gap".

Token design

Capability token (the long-lived credential)

  • 32 random bytes, hex-encoded (64 chars). Same pattern as the metadata-store encryption key.
  • Stored in SecretStorage as bergamot.capability_token.
  • Generated on first run; persists across extension restarts. The browser pairs once and keeps the token.
  • Presented as Authorization: Bearer <token> on every protected request.

Pairing secret (the short-lived bootstrap credential)

  • 16 random bytes, hex-encoded (32 chars). In-memory only — never persisted, never written to disk.
  • Generated fresh each server start.
  • Returned in /status as pair_secret — but only once, until the browser calls POST /pair. After that, /status no longer includes it and /pair returns 401 forever (until next restart).

Pairing flow — browser extension

The browser has no filesystem access, so it cannot read the token from port.json. Instead it gets it via /pair:

1
Extension
On startup: load (or generate) capability_token from SecretStorage. Generate fresh pairing_secret in memory.
2
Browser
Probes port range: GET /status. Response includes pair_secret (since pairing hasn't happened yet).
3
Browser
Checks chrome.storage.local for a stored token. No token found → calls POST /pair with body {"secret":"<pairing_secret>"}.
4
Extension
Validates secret matches in-memory pairing_secret. Returns {"token":"<capability_token>"}. Clears pairing_secret to null — one-time use.
5
Browser
Stores capability_token in chrome.storage.local (survives service-worker eviction). All future requests include Authorization: Bearer <token>.
6
Browser
On 401 from any request: clears stored token, re-discovers server (next server start will have a new pairing secret). Token is stable across restarts so 401 only occurs if the user reinstalled the extension.

MCP standalone authentication

The MCP process runs as the same user and has filesystem access. It authenticates by reading the token from ~/.bergamot/port.json:

  • The extension writes port.json with mode 0600 (owner-read/write only). Any process running as the user can read it — but not other users or world.
  • port.json now includes token: { "port": 5000, "pid": 12345, "token": "<capability_token>" }.
  • MCP reads the token and sends Authorization: Bearer <token> on all requests.
Why file not env var? The spawn in mcp_server_manager.ts could pass the token via BERGAMOT_TOKEN. But env vars are visible via /proc/<pid>/environ on Linux — no better than a 0600 file. Using port.json is consistent with how MCP already discovers the port, and avoids widening the spawn API.

Honest limits of this defense

AttackBefore task-40After task-40
Local process POSTs fake visits ✗ Succeeds ✓ Rejected — 401 without token
Local process reads query API / page content ✗ Succeeds ✓ Rejected — 401 without token
Local process races /status before browser and steals pairing_secret N/A ⚠ Narrow window (milliseconds at startup). After browser pairs, secret is consumed and /pair returns 401 forever.
Local process reads port.json to get token N/A ⚠ Possible for any process running as the user — file is 0600, not encrypted. This is the same bound as the OS keystore ACLs (adversary B: bounded, not solved).
Local process reads chrome.storage.local N/A ✓ Requires Chrome internals access — non-trivial for typical malware
Net assessment: This defense permanently closes the "any local process can call the API" gap. It does not stop a determined adversary B that can read files owned by the user — that is explicitly out of scope per the threat model.

What is NOT in scope

  • Token rotation / revocation command — YAGNI.
  • Securing /shutdown with the token — it's used by evict_stale_servers() which runs before the browser has paired; adding auth would break that flow.
  • Inbox encryption — tracked under task-39.
