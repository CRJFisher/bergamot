The page vector is produced by a batched embed pass, ahead of TDT

The pure page-vectorisation library (36.3) gains its production home. The page vector is built by a batched embed pass that runs ahead of a clustering run — not per-page on the capture hot path. The pass reads the already-cached public content, embeds every page missing a current-model vector in one batch off the event loop, and stores the result.

The one sentence

Embedding is a batched pass over the already-cached public corpus, run ahead of clustering on a worker off the event loop — built once per page via resolve_page_vector build-on-miss, written to topic_page_vector through the single writer; the capture path does no embedding at all, and TDT and RAG only ever read.

The batched embed pass — incremental over the cached corpus

Decision 1 — batched on a worker, model loaded per pass

The local embed is CPU-bound: onnxruntime-node inference is a synchronous, multi-second compute that would block the single-threaded event loop the /visit endpoint runs on. The settled design runs the pass on a worker, loads the model once per pass, and releases it after — so embedding never touches the capture hot path and the model is not resident around the clock.

Decision 1 — settled

Batched embed pass on a worker, model loaded once per pass and released after. The content is already durably cached at capture time, so embedding need not happen on arrival; batching gives one model load per pass and keeps the capture hot path entirely free of CPU embed work, with the model resident only while a pass runs rather than 24/7.

Decision 2 — what build-once-and-read does to determinism

The mitigation, best-effort and verified — not a hard gate

Pin ONNX Runtime single-threaded (intra_op_num_threads = 1, ORT_SEQUENTIAL, OMP_NUM_THREADS=1) to remove the float-non-associativity of multithreaded reductions. Bitwise reproducibility on this exact stack (transformers.js + onnxruntime-node, q8, x64) is not proven; add a regression test asserting byte-identical Float32 output and verify empirically rather than relying on it as an invariant.

The concrete DuckDB VectorStore — mirroring content_cache.ts

The store implements the pure library's VectorStore port (get / put) over the topic_page_vector table, in the encrypted metadata DuckDB file, written only through the single writer. It mirrors content_cache.ts: a create_*_schema step run by the writer, get / put, and the batch delete surface (delete_items / delete_by_url / delete_by_origin) with the CHECKPOINT-after-delete discipline the forget cascade depends on.

// One embedding per (page, model) in the ENCRYPTED metadata DuckDB file.
// Implements the @bergamot/tdt VectorStore port; written only via the single writer.
export async function create_page_vector_schema(db: DuckDB): Promise<void> {
  await db.exec(`CREATE TABLE IF NOT EXISTS topic_page_vector (
    page_session_id    TEXT NOT NULL,      -- soft ref → activity_sessions.id
    embedding_model_id TEXT NOT NULL,      -- e.g. 'bge-small-en-v1.5/q8/384#repr-v1'
    vector             FLOAT[] NOT NULL,   -- L2-normalized; dim fixed by the model id
    repr               TEXT NOT NULL,      -- forensic column, NOT part of the key
    built_at           TEXT NOT NULL,
    PRIMARY KEY (page_session_id, embedding_model_id)
  )`);
}

export class PageVectorStore implements VectorStore {
  constructor(private readonly db: DuckDB) {}

  async get(id: string, model_id: string): Promise<Float32Array | null> {
    const row = await db.query_first(`SELECT vector FROM topic_page_vector
       WHERE page_session_id = $id AND embedding_model_id = $m`, { id, m: model_id });
    return row ? Float32Array.from(row.vector as number[]) : null;
  }

  async put(id: string, model_id: string, repr: string, vector: Float32Array) {
    await db.execute(`INSERT INTO topic_page_vector
       (page_session_id, embedding_model_id, vector, repr, built_at)
       VALUES ($id, $m, $v, $r, $t)
       ON CONFLICT (page_session_id, embedding_model_id) DO UPDATE SET
         vector = excluded.vector, repr = excluded.repr, built_at = excluded.built_at`,
      { id, m: model_id, v: Array.from(vector), r: repr, t: new Date().toISOString() });
  }

  // Right-to-forget surface — mirrors ContentCache; CHECKPOINT folds deletes out of the WAL.
  async delete_items(ids: string[]): Promise<void> { /* DELETE … WHERE page_session_id IN (…) ; CHECKPOINT */ }
}
Why it lives in the metadata file, not a second store

LanceDB was rejected — it cannot be encrypted at rest while searchable, and content-derived vectors are sensitive. DuckDB serves similarity search natively via array_cosine_similarity over fixed-size FLOAT[dim] columns, so the encrypted metadata store covers both the get/put cache (all TDT needs now) and the deferred RAG search path. Under the single-writer rule the store opens no file handle of its own.
