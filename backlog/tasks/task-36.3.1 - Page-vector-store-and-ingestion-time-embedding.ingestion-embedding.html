The page vector is produced by a batched embed pass, ahead of TDT

The pure page-vectorisation library (36.3) gains its production home. The page vector is built by a batched embed pass that runs ahead of a clustering run — not per-page on the capture hot path. The pass reads the already-cached public content, embeds every page missing a current-model vector in one plain async loop off the JS event loop, and stores the result through the single writer.

The one sentence

Embedding is a batched async pass over the already-cached public corpus, run ahead of clustering with inference off the JS event loop (no worker thread) — built once per page via resolve_page_vector build-on-miss, written to topic_page_vector through the single writer; the capture path does no embedding at all, and TDT and RAG only ever read.

The batched embed pass — incremental over the cached corpus

Decision 1 — a plain async pass, no worker thread

The embed pass is a plain async loop on the extension host, not a worker thread — inference already runs off the JS event loop on libuv, and a worker could not hold the single-writer DuckDB anyway.

meets it partial / caveat fails it
Decision 1 — settled (no worker)

A plain async embed pass with a setImmediate yield between pages — no worker thread. Two facts make a worker unnecessary and unworkable: onnxruntime-node already runs inference off the JS event loop on libuv’s threadpool, so the loop never blocks; and a worker_threads worker could not open the single-writer metadata DuckDB to read the corpus or write the store. The pass runs on the host that owns the writer, batched ahead of a run, with the model loaded once per pass and released after.

Decision 2 — what build-once-and-read does to determinism

The mitigation, verified on x64 — best-effort, not a hard gate

ONNX Runtime is pinned single-threaded sequential via the pipeline’s session_options (intraOpNumThreads:1, interOpNumThreads:1, executionMode:"sequential"), removing the float non-associativity of multithreaded reductions. On the Intel x64 / q8 stack the same text now embeds byte-identically across runs and a reload — verified out-of-process by scripts/verify-embedder.mjs (npm run verify:embedder), because onnxruntime-node’s native typed-array check is incompatible with jest’s VM realm. It stays best-effort across other platforms (built-once-and-read makes it non-load-bearing), never a release gate.

The concrete DuckDB VectorStore — mirroring content_cache.ts

The store implements the pure library's VectorStore port (get / put) over topic_page_vector in the encrypted metadata DuckDB file, written only through the single writer — upserting on the composite key, opening no connection of its own.

new vscode/src/tdt/page_vector_store.ts  ·  the VectorStore over topic_page_vector (table created in create_metadata_schema)
// One embedding per (page, model) in the ENCRYPTED metadata DuckDB file.
// Implements the @bergamot/tdt VectorStore port; written only via the single writer.
// Created with the rest of the metadata schema (create_metadata_schema).
async function create_topic_page_vector(db: DuckDB): Promise<void> {
  await db.exec(`CREATE TABLE IF NOT EXISTS topic_page_vector (
    page_session_id    TEXT NOT NULL,      -- soft ref → activity_sessions.id
    embedding_model_id TEXT NOT NULL,      -- e.g. 'bge-small-en-v1.5/q8/384#repr-v1'
    vector             FLOAT[] NOT NULL,   -- L2-normalized; dim fixed by the model id
    repr               TEXT NOT NULL,      -- forensic column, NOT part of the key
    built_at           TEXT NOT NULL,
    PRIMARY KEY (page_session_id, embedding_model_id)
  )`);
}

export class PageVectorStore implements VectorStore {
  constructor(private readonly db: DuckDB) {}

  async get(id: string, model_id: string): Promise<Float32Array | null> {
    const row = await db.query_first(`SELECT vector FROM topic_page_vector
       WHERE page_session_id = $id AND embedding_model_id = $m`, { id, m: model_id });
    return row ? Float32Array.from(row.vector as number[]) : null;
  }

  async put(id: string, model_id: string, repr: string, vector: Float32Array) {
    if (vector.length === 0 || !vector.every(Number.isFinite))
      throw new Error("refusing to store an empty/non-finite page vector");
    await db.execute(`INSERT INTO topic_page_vector
       (page_session_id, embedding_model_id, vector, repr, built_at)
       VALUES ($id, $m, $v, $r, $t)
       ON CONFLICT (page_session_id, embedding_model_id) DO UPDATE SET
         vector = excluded.vector, repr = excluded.repr, built_at = excluded.built_at`,
      { id, m: model_id, v: Array.from(vector), r: repr, t: new Date().toISOString() });
  }

  // Last line of defence: never store a degenerate vector (AC #7).
  // resolve_page_vector already excludes no-text / sub-epsilon pages upstream.
}
Why it lives in the metadata file, not a second store

LanceDB was rejected — it cannot be encrypted at rest while searchable, and content-derived vectors are sensitive. DuckDB serves similarity search natively via array_cosine_similarity over fixed-size FLOAT[dim] columns, so the encrypted metadata store covers both the get/put cache (all TDT needs now) and the deferred RAG search path. Under the single-writer rule the store opens no file handle of its own.

The local embedder — offline, load-once-per-pass, single-thread

Load-bearing version pin

@huggingface/transformers is pinned EXACT at 3.7.6 because its onnxruntime-node 1.21.0 still ships the darwin-x64 native binary the Intel-Mac target needs — the 4.x line (onnxruntime-node 1.24.x) dropped it. Bumping the package requires re-running npm run verify:embedder and confirming the new onnxruntime still carries a darwin-x64 binary.

The batched embed pass — vectorise ahead of TDT

Iterate the cache-served public corpus, resolve each page via resolve_page_vector build-on-miss, persist via the store. A plain async loop — inference off-loop on libuv, a setImmediate yield between pages, no worker thread. ServerManager.embed_pages() runs it under a single-flight latch (one model load, no racing writes); the bergamot.tdt.embedPages command triggers it, and it is the step a clustering run calls before reading vectors. Incremental: one embed per new public page, a repeat pass a no-op.

Right-to-forget cascade entry + extended tests
