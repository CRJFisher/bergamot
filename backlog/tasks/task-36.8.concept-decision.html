The surface decision — why not raw MCP, and the two-layer split

Temporal Topic Detection produces topic clusters with a 36.5 label bundle. How does a user see and act on them? The answer is a two-layer split: one thin integration primitive at the database, and several user-facing surfaces that layer on top of it — never a bag of raw MCP tools that lets the schema dictate the experience.

The question, and the reflex that is rejected

What the DB-shaped-UX failure looks like, concretely

The raw-tool failure modeWhat the user actually faces
Opaque keys. list_topic_clusters returns a JSON array keyed by run_id and a hash id (ClusterRecord.id = hash(run_id | local_label), types.ts:56). To see members they must call get_topic_cluster(id) with an opaque id, and to know which run is current they must understand the status='complete' lifecycle and filter superseded runs themselves.
Double-surfacing. Retained historical runs ("running" | "complete" | "failed" | "superseded", types.ts:50) are not filtered for them. The same page appears across multiple retained runs — read as instability rather than history.
Leaked DB encodings. scope is a TEXT column with an unpinned serialization (types.ts:66); keyphrases is a raw array; representation_version is internal lineage. Each consumer must re-derive meaning from a raw DB-encoded blob.
The triple-edit tax. Any new cluster capability means a new ListTools entry plus a CallTool switch case plus a /query/topic_* route — the exact pattern at mcp_server_standalone.ts:74-176. The schema's shape dictates the call graph; growth is mechanical edit-in-three-places.
Surfaces nothing on its own. The constitution requires clusters be pushed at a habit anchor (constitution.md:127: "a VS Code panel that opens on launch and/or a weekly notification — not left purely pull"). A bag of pull-only tools cannot satisfy a push-surface mandate; the hero loop becomes something the user must remember to invoke — which means it is never seen.
The conflation that is the actual mistake

Raw MCP tools conflate two genuinely different things — the read contract over the tables and the human-facing experience — and let the first dictate the second. The fix is to split them.

How to read the columns

Scan a column, not a row. Host portability separates the field hardest: primitive / write-back / skill all score 5; the webview alone scores 1 — that single column is why the webview lands off the launch critical path. PKM visibility is the write-back's column (5): a note in the user's own vault, surfaced without asking. Actionability is the skill's column (5). No single surface wins every column — which is exactly why they layer.

Layering recommendation — backbone, actionability, control, accessory

Two terms used below

Required day-one user controls. The user must be able to manage the clusters Bergamot shows them: rename a mislabeled cluster, hide one they don't want, and tell Bergamot to never cluster a given site (e.g. a bank or health portal). The constitution requires these to ship together with the very first surface — "the control surface is what converts surveilled into seen" (constitution.md:128). "Launch-blocking" just means we cannot ship clusters to users without them.

Where they live. These actions are recorded by the skill into one small Bergamot-owned table (not the user's notes — see the privacy doc). Because the skill runs on every host, the controls work everywhere. Building them only into the VS Code webview would leave users on other PKM hosts unable to control their own clusters, so the webview is an extra place to expose them, never the only one.

RoleSurfaceWhy it earns this role
backbone Note-stub write-back → bergamot.staging/ The most PKM-native surface and the literal hero-loop deliverable: a markdown note in the user's own tool, surfaced ambiently without asking. As a pure filesystem write it is the universal fallback that ports to every PKM host. This is the SURFACE-node spine.
actionability The Claude skill (also drives stub generation) Invoked mid-task it answers "what have I been reading about X" and pulls cluster members with live exemplar URLs into the conversation. Crucially summarise_cluster → draft_note_stub seeds the backbone — one skill both answers in-context and writes staged stubs. Host-agnostic push vehicle (on-demand + scheduled weekly digest); cheapest surface; mirrors the proven weekly-interests template.
user controls · required day one The skill, writing to a control table (works on every host) The user must be able to correct the clusters they're shown — rename a mislabeled one, hide one, and mark a site as never-to-be-clustered. The constitution makes this required on the first day any surface ships (constitution.md:128): clustering someone's browsing without giving them these controls is surveillance, not a feature. The skill records each action by writing to one small Bergamot-owned table, so the controls work everywhere the skill runs. The webview can offer the same buttons more visibly for VS Code users, but it is never their only home — otherwise users on other hosts would have no way to control their clusters.
optional accessory VS Code webview Justified only for the VS Code host as a rich-visibility accessory and the most discoverable home for the control surface and launch panel. Explicitly NOT the cross-host strategy and NOT on the launch critical path: it serves only Wave 1, costs the most, and does not port to the daemon future. Build it after the backbone + skill prove the loop; resist scope creep — no PKM-write affordances from card clicks.
What this layering buys

It directly satisfies AC#2 ("every surface consumes one primitive") and the constitution's push-surface mandate without betting the hero loop — or the launch-blocking control surface — on the one host-locked, most-expensive surface. The push anchor for everyone is the skill's scheduled digest + the staged weekly stub; the control surface for everyone is the skill + control route; the webview is a richer home for VS Code users only.
