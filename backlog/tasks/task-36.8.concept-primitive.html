The integration primitive — one host-agnostic read API

Every surface — the note-stub write-back, the Claude skill, the VS Code webview — reads clusters through one thin module, cluster_reads.ts: four pure (db, params) → JSON functions over the live run. It is the only code that touches the cluster tables.

One module, four pure functions over the live run

The contract in one line

cluster_reads.ts is the only surface-facing code that JOINs topic_run × topic_cluster × topic_cluster_member. It returns plain JSON-serializable objects — no MCP types, no HTTP types, no VS Code types — drawn verbatim from the persisted 36.5 label-bundle fields, and reads only the live (status='complete') run.

The three page-status answers are distinct rows in the data

Noise is carried explicitly: a MemberRecord with is_noise = true, cluster_id = null (types.ts:76-77). So list_clusters_for_page distinguishes "clustered" (one or more clusters) from "noise" (processed in a live-run window but landed as HDBSCAN noise) from "unseen" (in no live-run window at all). Returning a bare empty array would conflate processed-and-noise with never-seen — the provenance and recall workflows depend on telling them apart, so that conflation is rejected.

Decisions this contract pins — recorded, not left implicit

DecisionWhat it pinsWhy
Expose coherence; hide representative_vectorcoherence is a cheap cluster-health signal; the FROZEN L2-normalized mean vector stays internal.The vector is a tracking input with no surface consumer — it bloats payloads and leaks an internal artifact (YAGNI).
Pin scope's JSON shape at the boundaryTop-k (domain, count) pairs.scope is a TEXT column with an unpinned serialization; consumers must never parse a raw DB-encoded blob.
list_clusters_for_page distinguishes clustered / noise / unseenNoise lives as an explicit row (is_noise = true, cluster_id = null)."You read this but it was a one-off in its window" is a different, honest answer from "this page has not been clustered."
Filter to status='complete' live runs in every operationSuperseded/running runs retained in history are excluded.Otherwise the same page or window double-surfaces and the user reads it as instability.
Multi-window reads, not "latest run" onlylist_clusters_in_range / window_coverage take (from, to).Dormant-thread resurfacing needs a time-range read across historical windows — run_id is per-window.
Read live, never cacheNo results held outside the DB.A cache would defeat the right-to-forget cascade (right_to_forget.ts:13).

What the primitive is NOT — the Stage-1 pipeline read

visits_in_window is a separate, still-required deliverable

The clustering pipeline reads its own input — captured visit metadata for a window — via GET /query/visits_in_window?from=&to= (plan §9). This route does not exist in server_manager.ts today. It is NOT part of cluster_reads.ts and NOT a user-facing surface: it reads webpage_* visit rows, not cluster rows, and feeds clustering, not a human. The §3 rename and the plan-§9 rewrite must preserve this requirement — it belongs to the pipeline's input path and survives the retirement of the raw-tool surface untouched.

In the daemon the functions bind to four Express routes reusing the proven relay mechanics verbatim — port.json discovery, param validation (400 on missing), MAX_QUERY_LIMIT = 100 clamping (server_manager.ts:72), res.json. Because the contract is a JSON shape rather than a table shape, a webview can ship for the VS Code host without the skill existing, the skill ships over stdio/HTTP for any host without the webview, and the write-back ships as a pure filesystem operation usable everywhere.

Before / after — the retired raw tools mapped onto one primitive

No half-built routes — and plan §9 must be rewritten surgically

No /query/topic_* routes exist today, so the slate is clean — this is purely about not re-creating them. But plan §9 still literally specifies the retired three-tool / /query/topic_* pattern (lines 772–877): leaving it unedited leaves a canonical doc describing the retired pattern (a documentation-form shim, constitution principle 12) that will mislead implementers into rebuilding exactly what AC#2 forbids. The rewrite deletes the raw-surface spec ONLY and explicitly preserves the visits_in_window Stage-1 bulk-read requirement — dropping it would orphan Stage-1. The cluster tables are added to the right-to-forget cascade (right_to_forget.ts:13 already names them).

Where it sits — between the tables and the three surfaces, across hosts

Why the split lets surfaces ship independently and per-host

Because the contract is a JSON shape, not a table shape, every surface depends on the stable JSON — never on the table layout. This is the market-validated pattern: Smart Connections exposes one embedding store through three intent-shaped surfaces (Connections / Lookup / Graph); Smart Graph treats "the graph as a decision surface" rather than a queryable table. Surfaces layer; they are not mutually exclusive.
