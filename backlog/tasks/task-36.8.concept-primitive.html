The integration primitive — one host-agnostic read API

Every surface — the note-stub write-back, the Claude skill, a future VS Code webview — reads clusters through one shipped module, vscode/src/tdt/cluster_reads.ts: four pure (db, params) → JSON functions over the live run. It is the only code that JOINs the cluster tables, and user curation is applied inside it.

One module, four pure functions over the live run

The contract in one line

cluster_reads.ts is the only surface-facing code that JOINs topic_run × topic_cluster × topic_cluster_member (plus webpage_* for page fields). It returns plain JSON-serializable objects — no MCP types, no HTTP types, no VS Code types — drawn from the persisted 36.5 label-bundle fields, reads only the live (status='complete') run, and applies the user's suppress/rename controls in-memory before any consumer sees a cluster.

The four operations — return shapes from the real 36.5 fields

OperationReturns (from the persisted cluster / member / run rows)
list_clusters_in_range(from, to, limit)
clusters overlapping [from, to), live run, newest-first; suppressed dropped + renames applied before the limit		 { id, run_id, display_label, headline_title, scope, keyphrases, size, coherence, time_span:{start, end}, representation_version }
Excludes representative_vector — internal tracking input, no surface consumer (YAGNI). The exemplar id is selected for control matching but dropped from the returned summary.
get_cluster(id)
members ordered probability DESC, page_session_id, capped at MAX_QUERY_LIMIT; null when unknown, not live, or suppressed		 { cluster:{…summary…}, exemplar_page:{page_session_id, url, title, page_loaded_at}, members:[{page_session_id, url, title, page_loaded_at, probability, is_exemplar}] }
Page fields LEFT-joined to webpage_activity_sessions + webpage_capture; the exemplar is resolved directly so it is present even if it falls past the member cap.
list_clusters_for_page(page_session_id)
live-run clusters containing that page		 { clusters:[…], page_status } where page_status ∈ {"clustered", "noise", "unseen"}.
page_status reflects the raw data; clusters reflects only non-suppressed clusters, so a clustered-but-suppressed page returns "clustered" with an empty array.
window_coverage(from, to)
per overlapping live run; control-independent		 { window:{start, end}, input_count, cluster_count, noise_count, coverage } where coverage = (input_count − noise_count) / input_count.
Derivable from topic_cluster_member alone; suppressing a cluster does not change that its pages were clustered.
The three page-status answers are distinct rows in the data

Noise is carried explicitly: a member row with is_noise = true. So list_clusters_for_page distinguishes "clustered" (a non-noise member of ≥1 live cluster) from "noise" (processed in a live run but landed as HDBSCAN noise — an honest "this was a one-off in its window") from "unseen" (in no live run at all). Returning a bare empty array would conflate processed-and-noise with never-seen; the provenance and recall workflows depend on telling them apart.

Decisions this contract pins

DecisionWhat it pinsWhy
Expose coherence; hide representative_vectorcoherence is a cheap cluster-health signal; the frozen L2-normalized mean vector stays internal and is never selected.The vector is a tracking input with no surface consumer — it bloats payloads and leaks an internal artifact (YAGNI).
Surface scope verbatimThe display-ready string the 36.5 labeler stored, e.g. "nextjs.org, github.com +3 sites" — returned as-is.The labeler already produces a display-ready string, so the primitive does not re-parse it or invent a structured shape. Describe the system as it is (YAGNI).
Apply controls in-memory, not via a SQL JOINcurate() drops suppressed clusters and applies renames against the resolved control maps inside cluster_reads.Controls key on a stable page identity (exemplar + label signature), never the per-run cluster id — they cannot be SQL-joined to a row that rotates each recompute. Applying them here makes this the single place curation takes effect.
list_clusters_for_page distinguishes clustered / noise / unseenNoise lives as an explicit member row (is_noise = true)."You read this but it was a one-off in its window" is a different, honest answer from "this page has not been clustered."
Filter to status='complete' live runs in every operationSuperseded / running / failed runs retained in history are excluded.Otherwise the same page or window double-surfaces and the user reads it as instability.
Multi-window reads, not "latest run" onlylist_clusters_in_range / window_coverage take (from, to).Dormant-thread resurfacing needs a time-range read across historical windows — run_id is per-window.
Read live, never cacheNo results held outside the DB.A cache would defeat the right-to-forget cascade.
Scope is a string, not a structured shape

An earlier pre-build sketch assumed scope needed pinning to (domain, count) pairs. The shipped 36.5 labeler already emits a display-ready string (e.g. "nextjs.org, github.com +3 sites"), so cluster_reads surfaces it verbatim — no re-parsing, no invented shape. Every surface renders the string directly.

What the primitive is NOT — the Stage-1 pipeline read

visits_in_window is a separate concern, owned by the orchestration work

The clustering pipeline reads its own input — captured visit metadata for a window — via a Stage-1 bulk read (GET /query/visits_in_window, plan §9). That is NOT part of cluster_reads.ts and NOT a user-facing surface: it reads webpage_* visit rows, not cluster rows, and feeds clustering, not a human. It belongs to the orchestration adapter (TASK-36.9) — the §9 rewrite preserves it untouched while retiring the raw-tool surface scope.

The routes reuse the proven relay mechanics verbatim — port.json discovery, param validation (400 on missing), MAX_QUERY_LIMIT = 100 clamping (mirrored both in the route and inside cluster_reads), res.json. Because the contract is a JSON shape rather than a table shape, the skill ships over the loopback for any host without a webview, the write-back ships as a pure filesystem op usable everywhere, and a webview can later ship for VS Code without changing the contract.

Tables → primitive → the shipped routes

Why the split lets surfaces ship independently and per-host

Because the contract is a JSON shape, not a table shape, every surface depends on the stable JSON — never on the table layout. This is the market-validated pattern: Smart Connections exposes one embedding store through three intent-shaped surfaces (Connections / Lookup / Graph); Smart Graph treats "the graph as a decision surface" rather than a queryable table. Surfaces layer; they are not mutually exclusive.
