the crux

Same API, two different at-rest guarantees

The store keys live in VS Code SecretStorage, which wraps them with a key from the OS keystore. On Linux with no keyring, Electron safeStorage silently swaps that wrapping key for a hardcoded one shipped in VS Code itself — store and retrieve still succeed, so nothing throws and the user sees no signal. The chain below is identical until the last hop.

working keyring — A is defended
no keyring →
degraded — A drops to obfuscation
wrapping key is secret — attacker with the files still lacks it wrapping key ships with VS Code — attacker with the files recovers it
why it matters · adversary A

Both encrypted stores — the durable metadata record and the content cache — rest on this one wrapping key. Degraded, an attacker with read access to the home directory can recover the data key from VS Code's files and decrypt everything. macOS Keychain and Windows DPAPI are unaffected.

the detection

Ask the session bus if a secrets service answers

An extension cannot query Electron's chosen safeStorage backend. The cheapest honest proxy: ping the Secret Service over the session D-Bus. If a service owns org.freedesktop.secrets and answers within 1.5 s, a real keyring exists; anything else means degraded.

vscode/src/database/linux_keyring.ts — the probe
// Only Linux can degrade; macOS/Windows return "available" without spawning.
if (process.platform !== "linux") return Promise.resolve("available");

// org.freedesktop.DBus.Peer.Ping is a no-arg liveness check — it proves a
// service actually OWNS the secrets name, not just that the bus exists.
// stdio:"ignore" — only the exit code matters; env is inherited so
// DBUS_SESSION_BUS_ADDRESS reaches dbus-send when a keyring is present.
const child = spawn("dbus-send", [
  "--session",
  "--dest=org.freedesktop.secrets",
  "--type=method_call",
  "--print-reply",
  "/org/freedesktop/secrets",
  "org.freedesktop.DBus.Peer.Ping",
], { stdio: "ignore" });

// settled-guard so the timer and the close/error handlers race exactly once.
const timer = setTimeout(() => { child.kill("SIGKILL"); settle("degraded"); }, 1500);
the detection · failure modes

Three ways the probe ends — only one means "available"

probe outcomewhat it meansresolves to
exit 0 A service owns org.freedesktop.secrets and replied to the ping — a real keyring backs SecretStorage. available · no warning
ENOENT dbus-send binary not installed — a session this minimal has no Secret Service either. degraded
timeout (≥1.5 s) No service replied / the bus is hung. Killed so activation never blocks on it. degraded
non-zero exit Bus reachable but nobody owns the secrets name (NameHasNoOwner, headless, --password-store=basic). degraded
the wiring

Where it sits in activation

Called from extension.ts right after get_or_create_store_key succeeds — so the warning is about a key that already exists. Two early exits keep it off the hot path on the platforms that can't degrade and after the user has already dismissed it once. The dismissed check runs before the probe, so an already-silenced session never spawns a process.

the signal

One time, two buttons, then quiet forever — when the doc opens

the gate · globalState

One flag controls everything

The warning reads context.globalState.get('bergamot.linux_keyring_warning_dismissed'). Falsy ⇒ eligible to show. The dismissed check runs before the probe, so a silenced session never spawns dbus-send.

Whether the flag gets written depends on which button — and, for "Learn more", whether the threat model actually opened.

the modal · showWarningMessage

Dismiss always silences · Learn more silences only on success

Dismiss — persists the flag immediately. Silent forever after.

Learn more — opens docs/threat-model.md via markdown.showPreview, then persists the flag only if the preview succeeded. If it throws (file not bundled in a packaged install), the flag stays unset and the warning re-appears next activation.

X / close — persists nothing; warning recurs while still degraded.

vscode/src/database/linux_keyring.ts — Learn more persists only after the doc opens
if (choice === dismiss) {
  // Dismiss always silences — persist immediately.
  await context.globalState.update(DISMISSED_KEY, true);
} else if (choice === learn_more) {
  // docs/ sits one level above extensionUri (bergamot/vscode → bergamot/docs).
  const doc_uri = vscode.Uri.joinPath(context.extensionUri, "..", "docs", "threat-model.md");
  try {
    await vscode.commands.executeCommand("markdown.showPreview", doc_uri);
    await context.globalState.update(DISMISSED_KEY, true); // only after it opened
  } catch {
    // Preview failed (not bundled in packaged install) — leave flag unset,
    // so the warning recurs and the threat model stays reachable in dev.
  }
}
// X / close (choice === undefined): persist nothing — recurs while degraded.
acceptance · AC#1 + AC#3

The warning is one-time (globalState gate), dismissible (Dismiss always persists), and links the threat model (Learn more opens it, persisting only on success). In docs/threat-model.md §A Key handling the detection is folded into the existing degradation sentence with an em-dash: "…weakens to obfuscation against offline file access — a one-time startup warning surfaces this degradation, links this threat model, and silences permanently once dismissed."

the posture · AC#2

accepted heuristic · the one seam

A running secrets service is a proxy for Electron's chosen backend, not proof of it — a user could force --password-store=basic while GNOME Keyring runs, and the probe would see the keyring and stay silent (a rare false negative). The warning never fires when a keyring is present, so it is never nagware; the residual gap is documented honestly in the threat model rather than papered over with a louder, noisier probe.
