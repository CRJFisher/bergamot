Validation harness and parameter sweep

Parameter choice is the load-bearing quality risk. A deterministic harness in tdt/src/validation/ sweeps a grid over real windows, scoring each cell by HDBSCAN-native validity (mean membership probability) plus noise fraction — always excluding label −1.

It runs the raw-dim vs PCA-50 A/B, confirms a known project recovers as a cluster, defines a noise/hubness guardrail whose PCA-promotion path is exercised, and persists the chosen operating point as config-data, not code.

The harness is a pure compute over already-resolved page vectors. sweep.ts composes the built cluster_window + represent_clusters stages (and PCA), scoring.ts holds the tf-free validity math and the AC#5 rollup, and operating_point.ts selects and persists the chosen cell — staying consistent with the package's pure, dependency-injected architecture.

The one sentence

The harness takes WindowInput[] = { window_start, window_end, visits, vectors } (parallel arrays of already-resolved page vectors) and, per grid cell, optionally reduces via deterministic PCA-50, builds the cosine distance matrix, fits HDBSCAN, and scores on the one signal the library actually exposes fit-only — mean membership probability over non-noise points, plus noise fraction and median size.

It does not claim silhouette or DBCV: the shipped silhouette is Euclidean-only and noise-naive, and clustering-tfjs 0.6.1 exposes no cluster_persistence attribute — so score_cell returns null (never 0) when a window has no cluster. Per-window scores feed aggregate_sweep, evaluate_guardrail, the pure select_operating_point() that picks the cell written to operating_point.json, and summarize_validation, which rolls the four AC#5 signals into one ValidationReport.

The harness data flow — vectors in, an operating point out

The honest validity metric — why mean membership probability, not silhouette

This is the subtlest point in the task. The clustering library ships a silhouette, but it is the wrong tool here for two verified reasons — so the harness scores on the one fit-only signal the library actually exposes.

The caveat stated plainly, so no one mistakes the metric for DBCV

"HDBSCAN-native validity" in this slice means mean membership probability, not a density-based DBCV score and not a cosine silhouette. The choice is forced by the library, recorded honestly, and is sufficient as a relative ranker across grid cells — the harness only needs to choose the best cell, not to publish an absolute coherence number.

The parameter grid — one upstream axis, four inner axes

PCA-50 A/B and the guardrail — raw by default, PCA as the escape valve

The lever order — minClusterSize-fraction first, target-N re-windowing second

Cross-window variance is the evidence gate, but it does not by itself activate the heavy windowing seam. The plan fixes an explicit lever order, and the harness's job is only to measure what gates the decision — not to pull the lever.

1

First lever — minClusterSize as a fraction of N

When per-window N varies a lot, the cheaper fix is to scale minClusterSize with window size so a busy month and a quiet one both demand a sensibly-sized cluster. This is tuned by the sweep within the existing windowing, and is tried before anything heavier.

plan §6 · the FIRST lever · a config/sweep change, not a structural one
2

Second lever — target-N re-windowing (the heavier seam)

Only if the first lever is insufficient is the target-N windowing seam (plan §5) activated to re-shape windows toward a roughly constant page count. The harness's cross-window variance of (N, cluster count, noise fraction) is the evidence that gates this decision — it does not flip it automatically.

plan §5 windowing seam · gated by measured cross-window variance · not in v1
What the harness measures vs what it decides

The harness reports cross-window variance and a boundary-fragmentation count (clusters whose time_span touches a window edge); it does not act on them.

Boundary fragmentation has a hierarchical fix — the Phase-4 tracker and the SOM macro tier, neither in v1 — so the count exists to size the problem before those slices are prioritised.

The chosen operating point flows into config as data, not code

The grid's starting defaults live in config.ts (code). The chosen point — what the sweep selected — lives in a JSON data file, parameterized by window unit, so re-tuning as history grows is a data edit, never a code change.

tdt/src/validation/operating_point.ts  ·  pure — picks the best grid cell; serialize / parse / load round-trip the JSON, validating the domain on read
// Pure selection: best cell = max mean membership probability, among cells in
// the healthy noise band [0.05, 0.65] that recover the known project AND have a
// non-null coherence signal. Throws if NO cell clears the gate (never selects a
// degenerate cell silently). config.ts keeps the grid + starting defaults.
export function select_operating_point(
  results: SweepResult[],
): OperatingPointEntry {
  const healthy = results.filter((r) =>
    r.mean_membership_probability !== null &&
    r.mean_noise_fraction >= HEALTHY_NOISE_FLOOR &&
    r.mean_noise_fraction <= HEALTHY_NOISE_CEILING &&
    r.known_project_recovered);                    // hard gate (AC#2)
  if (healthy.length === 0) throw new Error("no cell met the gate…");

  let best = healthy[0];                            // compare_cells: a total order —
  for (const r of healthy.slice(1))            // prob, then lower noise, then smaller
    if (compare_cells(r, best) < 0) best = r; // params, then raw before pca50
  return { ...best.cell };                       // the chosen OperatingPointEntry
}

// serialize_operating_point / parse_operating_point / load_operating_point
// round-trip the JSON; parse validates DOMAIN (min_cluster_size ≥ 2 integer,
// epsilon ≥ 0 finite, method "eom", reduction raw|pca50) so a stale or
// hand-edited value fails loud rather than silently mis-clustering a later run.
Determinism — three anchors hold across the sweep

HDBSCAN is bitwise-deterministic per tf backend; PCA uses a fixed random_state (power iteration, no SGD); and any timestamp (the operating-point selected_at) is injected, not Date.now(). Run the same window twice and the labels, probabilities, scores, and chosen cell are identical — so the sweep's verdict is reproducible.

Cadence evidence — the two numbers task-36.9 consumes

task-36.9 ships an automatic in-host trigger; the only open value is its cadence (default once/day). The harness records the two measurements that justify that default: how much the user actually browses, and how much work each run does.

Acceptance criteria — and how the harness meets each

Net effect — shipped (226 unit tests pass, both tsc configs clean)

Parameter choice is now evidence-based, not asserted: run_sweep ranks 108 cells per window by a metric the library actually exposes, the raw-vs-PCA decision is measured with a known-project safety gate, evaluate_guardrail has a tested escalation path, and the winning cell is persisted as re-tunable config-data.

Honest where the tooling forces it: there is no cluster_persistence attribute and the shipped silhouette is unusable, so the gate is mean membership probability — and score_cell returns null, not 0, for an all-noise window.

With no live capture DuckDB here, operating_point.json is seeded with the design default and re-written by select_operating_point against real windows later. The orchestrator (36.9) imports run_sweep directly and reads the cadence this harness measures.
