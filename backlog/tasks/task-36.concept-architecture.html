Architecture & the load-bearing constraint

@bergamot/tdt is a pure dependency-injected library. One database fact — DuckDB is single-writer per file — drives the whole asymmetric read/write design.

The package — a pure DI library, never touching VS Code

Why ports, not direct calls

Each external dependency — the database, the embedder, the cache, the write path — is one injectable contract. Tests supply fakes for all four, so the entire pipeline runs in memory; production supplies the real implementations.

The DuckDB single-writer constraint

The fact that drives everything else

Because TDT can never open the DuckDB file directly, its data access must be asymmetric: reads come through the extension, writes go through the extension's single writer. TDT computes; the extension persists.

The asymmetric read & write paths

The payoff of one shared DuckDB file

Cluster tables (topic_run, topic_cluster, topic_cluster_member, topic_page_vector) live in the same file as the capture tables, written only by the extension's writer. So windowed selection and the read path over clusters are plain single-DuckDB JOINs — no second store, no LanceDB, no separate topics.db (deferred, YAGNI). See pipeline & guarantees and the persistence sub-task.

Reaching the clusters — primitive vs surface, split in two

One primitive, many surfaces

Exposing raw read tools over the cluster tables would let the database shape the UX — a low-level surface with no curation and poor visibility into what the user has actually been browsing. Instead, one thin read API is the only thing on the DB; the surfaces that layer on top — and whether any is read-write to feed cluster-boundary curation back as a signal — are decided by the 36.8 spike, not assumed.

Dependency direction — acyclic, one-way
