Temporal Topic Detection — windowed HDBSCAN clustering (micro tier)

Turn the user's timestamped, passively-captured browsing into coherent projects / research threads — groups of highly-related pages — and reject one-off pages as noise. This is the first content consumer in the pipeline and the first slice of the TDT subsystem.

The one question this answers for the user

"What projects have I been working on, and which pages belong to each?"

Parent intention: why the micro tier exists

Bergamot's spine is capture → store → understand/surface. Capture stores browsing metadata only, never page content. The understand/surface node re-downloads the stored public URLs and makes sense of them. TDT is the first consumer of that re-download corpus — it runs ahead of the RAG pipeline (task-31).

The micro tier ships windowed HDBSCAN clustering. For each time window it groups page visits by embedding similarity (doc↔doc cosine over page vectors), producing clusters that read as candidate projects, and rejects one-off pages as noise rather than forcing them into a topic. A cluster = a set of pages = one candidate research thread.

Two axes are kept strictly separate:

  • Embedding axis — the only thing HDBSCAN clusters on (cosine over page vectors).
  • Time axis — used only for windowing (and later tracking). Time is never fused into the embedding.

The privacy filter is the login wall. Visits whose pages fail to re-download (auth-walled, paywalled, dead links) have no embedding and are excluded from clustering — they remain trail/metadata only. The clusterable corpus is the re-downloadable public subset. No ingestion-time content heuristic decides this; the re-download outcome does.

TDT is a new top-level npm workspace package @bergamot/tdt (sibling of vscode/ and browser/): a pure dependency-injected library plus thin adapters, depending only on injected port contracts and the clustering-tfjs library. It is independent of the RAG pipeline — it embeds pages with its own local model and never waits on task-31. The only nominal overlap with RAG is "both embed text," which is not a shared dependency.

Key architectural decisions

DecisionWhat it meansWhy
Dependency-injection pattern TDT is a pure library. Four injected port contracts — RelationalReader, EmbedFn, VectorStore, ClusterSink — express every external need. The extension supplies the concrete implementations; tests supply in-memory fakes. Makes the whole pipeline unit-testable without VS Code, DuckDB, or a network, and keeps clustering-tfjs and the embedding model swappable.
DuckDB single-writer constraint DuckDB is single-writer per file across processes. While the extension holds the file read-write (its whole lifetime), no other process can open it — even read-only. The extension is the only writer. This is the load-bearing fact that drives the port design: TDT never opens the DB file. Reads go through the RelationalReader port (in-process fns or HTTP /query/*); writes go through the extension's single-writer transaction behind ClusterSink.
No imports from vscode/src The @bergamot/tdt package never imports VS Code internals. The dependency arrow is one-way: vscode/ supplies deps to and calls into tdt/, never the reverse. Keeps TDT a clean, portable, testable library; the extension is just one possible host. Enforced by AC and a grep.
clustering-tfjs dependency The HDBSCAN engine. v1 needs pairwise_distance_matrix(X,'cosine') (shipped), the HDBSCAN estimator with metric='precomputed' emitting labels_/probabilities_/exemplarIndices_ (Phase 2), and select_medoids (Phase 3). It is an external prerequisite: the HDBSCAN upgrade is planned in the separate clustering-tfjs repo (its tasks 49–55) and gates the clustering sub-task. All library calls are isolated in one stage; the camelCase↔snake_case translation is quarantined at that boundary.
Cluster tables in the same DuckDB file topic_run / topic_cluster / topic_cluster_member / topic_page_vector live in the capture DB, written only by the extension's writer. Windowed selection and the MCP read path become plain single-DuckDB JOINs, consistent with the existing tools. A separate topics.db is deferred (YAGNI).
Determinism is a contract Window bounds are a pure function of (timestamps, config); stable fetch order, fixed-order float64 segment accumulation, and a pinned tf backend with a bitwise reproducibility regression test. Same captures + pinned model must produce identical clusters (parent AC #3). Windowing (36.2) is the first place this contract is enforced; HDBSCAN is fit-only with no RNG on this path.

  5. Representations + deterministic labeler

  6. Persistence
    topic_run / topic_cluster / topic_cluster_member, run-id hashing, idempotency (no-op / atomic-replace / supersede), is_noise coverage. Verify: re-run same key+fingerprint is a no-op; re-embed bumps input_fingerprint and re-clusters.
    task-36.6 — Persistence: cluster tables, run keying, idempotency
  7. Validation harness + parameter sweep
    Sweep window × minClusterSize × minSamples × epsilon on real windows; score by HDBSCAN-native validity + noise rate; A/B raw-dim vs PCA-50; confirm a known project recovers. Persist the chosen operating point as config. Verify: noise-rate guardrail trips → PCA promotion works.
    task-36.7 — Validation harness and parameter sweep
  8. MCP surface
    Three /query/topic_* routes + the visits_in_window route + three read-only MCP tools (list_topic_clusters, get_topic_cluster, list_clusters_for_page). Verify: tools return JSON mirroring the existing five; read-only.
    task-36.8 — MCP surface for topic clusters
  9. Trigger
    One VS Code command bergamot.tdt.rebuildClusters over a pure rebuild_clusters(window_spec) function. Compute runs OFF the extension-host event loop (worker/child process) so a dense O(n²) fit never freezes the UI or stalls capture; the writer persists results in one short transaction. No scheduler (YAGNI). Verify: clustering a real month produces browsable clusters via MCP without blocking capture.
    task-36.9 — Trigger and off-thread orchestration

How the sub-tasks compose into the parent goal

The pipeline is a straight line from the visit stream to browsable clusters. Each sub-task owns one stage; the stages hand typed values forward and never reach backward.

  visit stream
      │  36.2  windowing.ts ── bounded frames, each ≤ max_samples, deterministic
      ▼
  WindowSignal[]  ─ skip (sparse) ─▶ "not enough data yet"
      │  36.3  build_page_vector ── re-download → embed → L2-normalize → cache
      ▼
  PageVector[]    ─ auth-walled / failed re-download ─▶ excluded
      │  36.4  cosine distance matrix → HDBSCAN.fit  (the ONLY clustering-tfjs call)
      ▼
  HdbscanRaw      ─ label -1 ─▶ noise (not forced into a cluster)
      │  36.5  representations + deterministic labeler (no LLM)
      ▼
  RepresentedCluster[]
      │  36.6  persist: topic_run / topic_cluster / topic_cluster_member  (idempotent)
      ▼
  DuckDB tables ──▶ 36.8 MCP read tools ──▶ browsable clusters
      ▲
      └ 36.7 validation sweep picks + persists the operating parameters
      └ 36.9 trigger runs the whole thing OFF the event loop

Windowing (36.2) is where the determinism contract is first enforced. Because window bounds are a pure function of (timestamps, config), every downstream stage inherits a stable, reproducible set of frames — the precondition for parent AC #3 (identical captures → identical clusters) and for the future stateless cross-window tracker.

Parent acceptance criteria (task-36)

  1. A @bergamot/tdt workspace clusters a real time window of re-downloaded public pages into project groups end-to-end, browsable via MCP, without blocking capture; auth-walled / failed-re-download visits are excluded.
  2. TDT embeds pages with its own model and has no build-time or runtime dependency on the RAG pipeline (task-31).
  3. Clustering is deterministic and reproducible — same captures + pinned model produce identical clusters, verified by a regression test.
  4. One-off pages are surfaced as noise rather than forced into clusters; per-window cluster coverage / noise rate is queryable.
  5. Operating parameters are selected by a validation sweep on real data and persisted as config rather than hardcoded.
  6. The design draft remains the canonical reference and stays in sync with what ships.
  7. Every cluster/persistence store joins the right-to-forget cascade in vscode/src/right_to_forget.ts (constitution principle 4), with cascade tests extended.
