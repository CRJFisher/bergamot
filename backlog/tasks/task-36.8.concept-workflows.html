PKM workflows → surface mapping

Six concrete PKM workflows turn topic clusters into something a user sees and acts on. Every one consumes the single read primitive, the primary surface on the launch path is always host-agnostic, and exactly two workflows are read-write — one writes only to bergamot.staging/, the other only to Bergamot's own control tables.

The six workflows, by primary surface and access

The one thing to read off this page

The read-only/read-write split is the AC#4 answer. Toward the PKM, surfaces are read-mostly: the only PKM write is the note-stub, and it flows one way into staging with no feedback read back from the user's edits. Toward Bergamot's own state, curation is read-write and in scope now — launch-blocking, not a deferred seam.

All six consume one primitive

No workflow touches DuckDB. Each calls cluster_reads.ts through the host-agnostic JSON contract — in-process for the stub generator and webview, over the /query/cluster* relay for the skill. Surfaces layer; they are not mutually exclusive. The same skill that answers in-context recall also drives stub generation (summarise_cluster → draft_note_stub) and POSTs curation actions to the control route.

The read-only vs read-write decision, made visible (AC#4)

In scope now — not a seam

Cluster-boundary curation (suppress / rename / never-cluster-this-origin) ships with the surface on day one. It persists in a control table keyed to survive run_id recomputes, is itself a right-to-forget cascade target, and ships host-agnostic via the skill + control route — never gated on the VS Code webview.

The seam that is deliberately NOT built

PKM-edit-derived feedback is explicitly out of scope. Reading a user's stub edits back as curation (treating a rename/move as “approve”) would skirt the principle-8 boundary and is brittle. Stubs flow out to staging; nothing flows back from PKM edits. Conflating this with control-table curation is the brittle trap the decision avoids.

Why the noise distinction matters here

The provenance and recall workflows depend on page_status separating “you read this but it was a one-off in its window” (noise) from “this page has not been clustered” (unseen). The data carries noise as an explicit row, so the contract never collapses processed-and-noise into never-seen — an honest answer the surfaces surface as-is.
