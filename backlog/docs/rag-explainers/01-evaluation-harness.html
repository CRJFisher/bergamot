The evaluation harness

Before you change a single retrieval knob, build the ruler that tells you whether the change actually made things better.

01 The problem

Bergamot's retrieval baseline is deliberately minimal. Every re-downloaded public page is embedded as one whole-page vector using OpenAI's text-embedding-3-small model and stored in LanceDB. At query time the system embeds the query and returns the pages whose vectors are closest by dense cosine similarity — the angle between two embedding vectors, where closer means more semantically similar.

That is the whole pipeline. There is no chunking (splitting a page into smaller passages), no BM25 (a keyword-scoring algorithm that rewards rare exact-term matches), no reranking (a second model that re-scores the shortlist), and no query rewriting (reformulating the user's question before search). Most importantly, there is no evaluation at all.

Failure mode

Today nobody can say whether a change helped. Someone swaps the embedding model, adds chunking, or tweaks a prompt, eyeballs a few queries, and declares victory. Those "improvements" are vibes, not measurements. A change that looks great on the three queries you happen to test can silently regress the other ninety-seven. Without a number to compare against, every later phase of this roadmap would be guesswork.

02 How it works

An evaluation harness turns "did this help?" into a reproducible number. It has three moving parts: a fixed test set, a battery of metrics, and a discipline for reporting deltas.

The golden dataset

A golden dataset is a fixed list of queries, each paired with the set of pages (or chunks) that are known to be relevant — the ground truth. For Bergamot the golden set is drawn from the re-downloadable public corpus — the public pages re-downloaded from the user's visited URLs — so the queries and relevant answers reflect the real content the system actually serves, not a generic benchmark. Because the golden set is committed and frozen, every run is measured against the same ruler.

Retrieval metrics

These ask one thing: did the retriever surface the relevant material near the top? They look only at the ranked list of results, comparing it to the golden ground truth.

MetricWhat it measuresRewards
Recall@k Fraction of all relevant items that appear in the top k results. Not missing relevant material.
Precision@k Fraction of the top k results that are relevant. Not padding the top with junk.
MRR Mean Reciprocal Rank — 1 / rank of the first relevant result. Putting a good answer at position 1.
nDCG@k Normalized Discounted Cumulative Gain — relevance discounted by how far down the list it sits. Ranking relevant items higher, not just including them.

Generation metrics (the RAGAS family)

Retrieval metrics stop at the shortlist. Generation metrics judge the answer the LLM writes from that shortlist. They are scored by an LLM-as-judge — a separate model prompted to grade each output against the question and the retrieved context.

  • Context precision — of the retrieved context, how much is actually relevant (signal vs. filler).
  • Context recall — did retrieval pull in all the context needed to answer fully.
  • Faithfulness — is every claim in the answer grounded in the retrieved context, with no hallucinated additions.
  • Answer relevance — does the answer actually address the question that was asked.

The discipline

The harness is only useful if it is used consistently. The rule: every change reports a delta against a committed baseline. You run the same golden set through the old pipeline and the new one, and you publish both score sheets side by side. A phase "wins" only if the numbers move the right way.

04 Decision lens

When to build an evaluation harness

✓ Reach for it when

  • You are about to change retrieval and need proof the change helped, not a hunch.
  • You want regression safety — a guard that catches the day a "win" quietly breaks other queries.
  • You need portfolio or production credibility: a committed score sheet is the difference between "I think it's better" and "Recall@5 rose from 0.61 to 0.79."

✕ Skip / overkill when

  • It is a one-off throwaway script you will never tune or rerun.
  • The corpus is tiny enough that retrieval quality is obviously fine by inspection and there is nothing to optimize.

The tradeoff: building and maintaining a golden set has a real labeling cost, and the LLM-as-judge adds eval-time API cost plus its own noise — judges carry bias and can disagree run to run. But the alternative is flying blind. This harness is the precondition for every other phase: hybrid search, chunking, reranking, and query transformation are all defined by the delta they produce against this ruler. That is exactly why it is listed first.

05 In Bergamot

task-31.1 ships the harness and supersedes the older, broader task-30. Concretely it delivers:

  • A golden dataset built from Bergamot's own re-downloadable public corpus, stored in-repo so it is versioned and frozen.
  • A runnable harness computing the retrieval metrics — Recall@k, MRR, and nDCG@k — over that golden set.
  • RAGAS-style generation metrics (context precision, context recall, faithfulness, answer relevance) scored via an LLM-as-judge.
  • A committed baseline report for the current whole-page, pure-dense pipeline — the number every future phase must beat.
  • One comparable report format so every later phase produces a measurable delta against that baseline.
Why first

The roadmap puts evaluation in Phase A on purpose: it is the instrument that makes Phases B through H falsifiable. Build the ruler, then start measuring.
