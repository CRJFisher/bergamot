Generation surface: order, cite, and know when to skip retrieval

Retrieval can be perfect and the answer still wrong. How you arrange chunks in the prompt, whether you cite them, and whether you even need retrieval for a small corpus all decide whether the generator succeeds.

01 The problem

Bergamot's MCP semantic_search tool returns a 200-character preview blob for each hit — a slice of text with no source link, no chunk id, and no thought given to which order the hits land in the prompt or to how big the corpus is in the first place. The retrieval layer (an MCP, or Model Context Protocol, tool the model calls) hands back text and stops there. Everything that happens between "good chunks retrieved" and "good answer generated" is left to chance.

Failure mode

Retrieval can be perfect yet generation still fails. Relevant context buried in the middle of a long prompt gets ignored — the model literally reads past it ("lost in the middle"). The answer can't be traced to a source, because nothing came back but a text fragment, so the user can't tell if it's grounded or hallucinated. And for a small corpus you pay the full cost and complexity of a retrieval pipeline you never needed — the whole knowledge base would have fit in the prompt.

02 How it works

The generation surface is the thin layer that shapes retrieved results before they reach the model and the user. Four ideas do the work.

1 · Lost in the middle — order chunks to the edges

Large language models do not attend evenly across a long context. They attend most to what sits at the start and the end, and recall sags in the middle — plot accuracy against the position of a key fact and you get a U-shaped curve: high at both ends, lowest in the centre. A fact placed at position 6 of 11 can be quietly ignored even though it's right there in the prompt.

The mitigation is free: reorder retrieved chunks so the most relevant sit at the edges. Put the best chunk first, the second-best last, and let the weaker ones fill the soft middle. Same chunks, same tokens — better recall, just by arrangement.

2 · Citations / attribution — make answers traceable

Return each result's source URL and chunk id alongside its text. Now every claim in the generated answer can be traced back to a specific document and span. Attribution turns an ungrounded blob into something a reader can verify and trust — and lets an agent surface "according to this page" instead of an anonymous fragment.

3 · Structured outputs — typed results, not prose

Return typed result objects — fields like title, url, chunk_id, score, text — not a single prose blob. An agent consuming the tool can then read each field reliably: sort by score, deduplicate by url, render a citation, decide what to keep. Structure is what makes results machine-consumable rather than something the model has to re-parse out of free text.

4 · Small-corpus short-circuit — sometimes skip retrieval entirely

Per Anthropic's guidance: if your entire knowledge base is under ~200,000 tokens (roughly 500 pages), you can skip retrieval altogether and put the whole corpus directly in the prompt. No index, no embeddings, no ranking — the model sees everything, so there is nothing to miss. It's simpler and often better. The threshold isn't arbitrary: it tracks the model's context-window size, so as context windows grow, more corpora cross over into "just stuff it all in."

The throughline

The first three ideas are cheap, high-trust polish on a retrieval pipeline: order the chunks, attach provenance, type the output. The fourth is a genuine architecture fork — below the threshold the right move is to not build a RAG pipeline at all.

04 Decision lens

      

        When to invest in the generation surface — and when it's moot
        

          

            
✓ Reach for it when

            
    
              
  • You return multiple chunks into a long prompt — order them so the best sit at the edges.
    • 
              
  • Answers need to be trusted and traceable — attach citations (source URL + chunk id).
    • 
              
  • Agents consume your results — return structured outputs they can read field by field.
    • 
              
  • Corpora vary in size — short-circuit the small ones straight into the prompt.
    • 
            

          

          

            
✕ Skip / overkill when

            
    
              
  • You only ever return 1–2 chunks — there's nothing to order, so the U-curve fix is moot.
    • 
              
  • It's a private throwaway tool where provenance doesn't matter — citations buy you nothing.
    • 
            

          

        

        
Tradeoff: ordering, citations, and structured outputs are cheap, high-trust polish — mostly formatting plus a size check, with little runtime cost. But the small-corpus short-circuit is a genuine architecture fork: below the threshold, the simplest "stuff it all in" design beats a full RAG pipeline. Don't over-engineer a retrieval stack for a corpus that fits in the window.
