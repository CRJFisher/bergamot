Building a production RAG pipeline

Ten hands-on explainers — one per implementation phase — covering how each retrieval technique works and, more importantly, how to decide when to reach for it.

These pages are the learning companion to backlog/docs/rag-pipeline-upgrade-plan.md and tasks task-31.1–task-31.9 plus task-31.11 (time-aware retrieval). Each one is self-contained and interactive: open it and play with the demo. Every page ends with a Decision lens — the when-to-use-vs-skip reasoning that separates copying a tutorial from engineering a system.

The one idea to take away

Sophistication is not the goal — measured fitness for your corpus is. The plan is ordered by return on effort: measure first, then the cheap high-impact retrieval upgrades, and only reach for advanced architectures when a measured problem demands them. Most teams never need the last page.

03 How to read the order

The sequence is not the order of the data flow — it's the order of return on effort:

  1. Measure first (A). Without a baseline you can't tell an improvement from a regression.
  2. Then the cheap, native win (D). Hybrid search is almost free on LanceDB and immediately broadens recall.
  3. Then the biggest quality lever (C). Contextual chunking is the single largest retrieval-quality gain — but it costs a one-time LLM pass, so it follows the free win.
  4. Then stack reranking (E). It compounds with C and D for the largest cumulative gain.
  5. Inputs & model (B, G) raise the ceiling; query transforms & generation polish (F, H) are marginal or trust-focused.
  6. Advanced architectures (31.9) stay deferred until a measured problem the baseline can't solve appears.
Numbers caveat

Retrieval-improvement percentages quoted in these pages (e.g. −35% / −49% / −67% failure reduction) are Anthropic's own benchmarks on their own technique — accurate as cited, but best-case vendor figures, not independently reproduced. That is precisely why Phase A measures every change on Bergamot's own corpus.
