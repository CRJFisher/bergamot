Deferred architectures: when advanced RAG is overkill

Knowing what not to build is a senior skill. This capstone is about the decision that precedes every advanced RAG architecture — measuring whether you actually have the problem it solves before you pay its cost.

01 The problem

The RAG literature moves fast, and it is tempting to reach for the most advanced architecture you have read about this week — a knowledge graph here, an agent swarm there. The newest paper always sounds like the obvious next step. But an architecture is only an asset if it solves a problem you can measure, and most teams never reach the point where they need more than a well-built baseline.

Failure mode

Adopting GraphRAG, Agentic RAG, Self-RAG, or CRAG before the baseline (contextual chunking + hybrid search + reranking) is even built and measured. This adds large cost and operational complexity to solve problems Bergamot may not actually have — premature sophistication. The discipline here is YAGNI: you aren't gonna need it until a measurement says you do.

The right move is the opposite of dropping these techniques: name them, understand them precisely, and defer them behind a written trigger that says when to revisit. The rest of this page is the primer plus the decision tool.

02 How it works — four architectures

Each architecture below targets a specific gap that a single-shot "embed, retrieve top-k, generate" pipeline cannot close. To decide, you need to know exactly what each one solves, how it works, and what it costs.

GraphRAG (Microsoft)

GraphRAG uses a language model to extract an entity knowledge graph from the whole corpus — nodes are entities (people, projects, concepts) and edges are the relationships between them. It then runs community detection to cluster closely-related entities into groups, and pre-generates a summary for each community during indexing. To answer a global, sensemaking question — "what are the main themes across everything?" — it runs map-reduce over those community summaries: summarize each community's take (map), then combine into one answer (reduce). Naive RAG fails on these queries because the answer is not contained in any handful of local chunks; it is a property of the corpus as a whole. In Microsoft's evaluation, GraphRAG improved answer comprehensiveness and diversity over a conventional RAG baseline, with reported win rates around 57–64%. Read that with care: it is an LLM-as-judge evaluation (a model grading answers, which carries known position and length biases), and the approach pays a real indexing cost — a heavy LLM pass over the corpus plus a graph store to maintain.

Agentic RAG

Agentic RAG embeds autonomous agents into the pipeline. Instead of one fixed retrieve-then-generate step, agents use reflection (critiquing their own intermediate results), planning (breaking a question into sub-steps), tool use (calling search, calculators, APIs), and multi-agent collaboration to dynamically manage retrieval across multi-step reasoning. This overcomes the ceiling of static, single-shot RAG, which cannot decide mid-answer that it needs to go look something else up. The cost is heavy: many LLM calls per query and real orchestration complexity (loops, state, failure handling) to keep agents from spinning.

Self-RAG

Self-RAG trains a single language model to retrieve on demand and self-critique using special reflection tokens it emits during generation. These tokens let the model decide whether retrieval is even needed for the current span, and then grade the retrieved passages (are they relevant?) and its own output (is it supported and useful?). The catch: this behaviour comes from custom model training, not prompting. That puts it out of scope for a TypeScript/Node application that consumes models through an API rather than fine-tuning them.

CRAG (Corrective RAG)

CRAG adds a lightweight retrieval evaluator — a small model that scores how good the retrieved documents are for the query. Based on that score it triggers one of three actions: Correct (refine and use the docs), Ambiguous (blend strategies), or Incorrect (the local docs are bad). On a poor score it falls back to web search to bring in external knowledge. It is deliberately plug-and-play: it bolts onto an existing RAG pipeline rather than replacing it. The cost is modest by comparison — an extra evaluator plus a dependency on an external web-search service.

04 Decision lens

Decision lens — advanced / deferred architectures

For a baseline personal knowledge manager, contextual chunking + hybrid search + reranking is the sweet spot. The architectures below are deliberately deferred — recorded with revisit triggers, not dropped.

✓ Reach for one when

  • You have a specific, measured problem the baseline can't solve:
  • global summarization → GraphRAG
  • multi-hop reasoning → Agentic RAG
  • persistent retrieval failure → CRAG
  • …and you can absorb the cost.

✕ Skip / overkill when

  • You haven't measured the baseline yet.
  • You're adopting it because it's fashionable, not because a metric demands it.
  • The need is hypothetical ("users might one day…").

Tradeoff: each adds substantial cost — GraphRAG a heavy LLM indexing pass plus a graph store; Agentic RAG many LLM calls and orchestration; Self-RAG custom training; CRAG an evaluator plus an external web-search dependency. Defer deliberately, with a written trigger.

05 In Bergamot

Task task-31.9 ships a decision record (under backlog/decisions/) documenting GraphRAG, Agentic RAG, Self-RAG, and CRAG. For each architecture it captures three things: the problem it solves, why it is deferred now, and the concrete trigger to revisit — linking back to backlog/docs/rag-pipeline-upgrade-plan.md so the baseline work and the deferred work stay connected.

The point is not avoidance. Deferring deliberately — with a written trigger that says exactly when to come back — is itself the engineering decision. It keeps the codebase simple today while making the upgrade path explicit for the day a measurement finally justifies it.
