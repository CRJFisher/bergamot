Phase B · task-31.5 · Ingest

Clean ingestion

Before you embed a single web page, strip out the nav bars, cookie banners, and "related links" — because whatever you embed is what you will retrieve. The HTML here is the re-downloaded public page, fetched from the stored URL in post-processing — not page content captured at browse time.

01 The problem

Bergamot ingests the open web. When it re-downloads a page from its stored URL, it does not get a clean article — it gets the whole rendered HTML document: the navigation bar, the cookie-consent banner, ad containers, a "related links" sidebar, social-share widgets, and a footer full of links. The actual article you care about is a small subtree buried inside all of that chrome — the term for the repeating surrounding furniture of a site (menus, headers, footers) that frames every page but is not the content of any one page.

That chrome is boilerplate: near-identical text that appears on thousands of pages across a site. If you embed the page as-is, the boilerplate goes into the vector right alongside the article. An embedding — the numeric vector that captures a passage's meaning — gets diluted when it has to summarize "deep dive on React hooks" and "Subscribe to our newsletter · Privacy Policy · © 2026" in one averaged direction.

Failure mode

Garbage in, garbage vectors out. Boilerplate text gets embedded alongside the article, diluting the page vector so it no longer points cleanly at the topic. Worse, the boilerplate itself becomes retrievable: a generic phrase like "Subscribe to our newsletter" lives on every page, so it matches far too many queries and surfaces irrelevant pages. The chrome you never wanted is now competing with real answers for a slot in the results.

02 How it works

The fix is main-content extraction: isolate the article subtree and throw the rest away, before anything is embedded. Bergamot does this the cheap, robust way — with heuristics (fixed rules), not a trained model. This is the approach popularized by Trafilatura, an open-source extraction library. A heuristic extractor is fast, dependency-light, and qualitatively competitive with neural extractors (machine-learning models trained to find content) while being far simpler to run inline on every re-download.

Step 1 — Prune by tag

Walk the DOM tree (the parsed structure of the HTML, where every element is a node) and remove whole subtrees whose element type is structurally boilerplate. These tags almost never hold the article: <nav> (navigation menus), <aside> (sidebars), <footer> (page footers), <form> (search and signup forms), <iframe> (embedded third-party frames), plus ad, <script>, and <style> nodes. Dropping them by tag alone clears most of the chrome in one pass.

Step 2 — Prune by link density

Some boilerplate hides inside generic containers that a tag rule misses — a <div> that is really a link farm. The signal that catches it is link density: the ratio of anchor-text characters (text wrapped in clickable <a> links) to the total characters in a block.

link density = (characters inside <a> links) / (total characters in block)

Prose runs low: an article paragraph is mostly plain sentences with the occasional inline link, so its density is near 0.05. A nav bar, a "related links" list, or a footer is almost entirely clickable text, so its density is high — 0.7 to 0.9. A block whose link density sits above a threshold is read as a menu or link list rather than writing, and dropped.

Step 3 — Keep the article, then hand off

What survives both passes is the main article subtree. Bergamot serializes it to clean markdown (lightweight plain-text formatting) and only then runs the existing LLM content step and the embedding model. Every downstream stage now sees the article and nothing else.

raw HTML ─▶ prune by tag ─▶ prune by link-density ─▶ clean markdown ─▶ LLM content + embeddings │ │ │ │ │ re-down- drop nav/ drop high-link- article subtree what actually loaded URL aside/footer/ density blocks only, as markdown gets embedded form/iframe/ (menus, link ad/script/style farms)

04 Decision lens

      

        When to run heuristic main-content extraction
        

          

            
✓ Reach for it when

            
    
              
  • Your source is raw web HTML — scraped or re-downloaded pages with heavy chrome. This is
                exactly Bergamot's case: every re-download is a full rendered document.
    • 
              
  • You want clean vectors and clean LLM input cheaply — fast, fixed-rule extraction with no
                model to host or pay for.
    • 
              
  • The boilerplate is generic enough that it would pollute retrieval ("newsletter", "privacy
                policy") if left in.
    • 
            

          

          

            
✕ Skip / overkill when

            
    
              
  • Inputs are already clean — markdown notes, API docs, plain text. There is no chrome to
                strip.
    • 
              
  • Content lives in well-defined semantic regions a simple CSS selector already isolates, so
                you do not need density heuristics at all.
    • 
            

          

        

        

          The tradeoff: heuristic extraction is fast and dependency-light, but it is not perfect.
          It can over-prune — clipping a legitimate aside that happened to look link-heavy — or
          under-prune on unusual layouts that dodge the rules. Even so, it is a quality-of-inputs win
          that compounds with every downstream stage: cleaner chunks, cleaner embeddings, cleaner LLM context, all from
          one cheap pass. It depends on nothing else, so it can land in parallel with chunking.
          Garbage in, garbage out — clean the inputs before you embed.
        

      

    


    
    

      
05 In Bergamot

      
task-31.5 inserts heuristic main-content extraction into the post-processing pipeline, after re-download. Concretely it ships:

      
    
        
  • Re-downloaded public HTML passes through heuristic main-content extraction — pruning
          nav, footer, aside, ad, and social-share blocks — before the LLM content step, not after.
    • 
        
  • The extracted markdown is measurably cleaner: less boilerplate on a set of sample noisy pages,
          verified by comparison against the raw re-download.
    • 
        
  • Neutral-or-better retrieval quality on the evaluation harness — the extraction never regresses
          the committed baseline, and on noisy pages it improves it.
    • 
      

      

        Why Phase B
        

          Extraction sits early because it lifts the floor for everything after it. Chunking, hybrid search, reranking, and
          generation all inherit cleaner text the moment ingestion stops feeding the pipeline chrome. It is the smallest
          change with the widest blast radius.
        

      

      

        Fidelity caveat
        

          Because the HTML is re-downloaded from the URL rather than captured as viewed, it may differ from
          the page the user actually saw: dynamic/JS-rendered content, A/B variants, paywall or consent drift, and edits over
          time all diverge, and login-walled or dead pages do not re-download at all (they stay metadata-only and are excluded).
          Re-download fidelity is tracked with fetched_at + a content hash + HTTP status so drift and unavailability
          are visible; a citation references the URL and metadata, not a byte-for-byte snapshot.
