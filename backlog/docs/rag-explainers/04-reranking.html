Reranking: a precise second pass over the shortlist

Fast retrieval gives you a roughly-ordered shortlist. A reranker reads each candidate against the query together and reorders them by true relevance — so the best passage isn't left stranded at rank 7.

01 The problem

Even after hybrid retrieval (dense vectors plus BM25, fused), the top-k ordering you get back is approximate. Vector and keyword scores are cheap proxies for relevance — they rank well enough to surface the right region of the corpus, but they routinely misjudge which of the close candidates is actually best. The truly best passage can sit at rank 6 or 7 while three weaker passages crowd the top.

That ordering matters because the context window is finite. If you only feed the generator the top 3–5 passages, a best-answer stuck at rank 7 never reaches the model — the system retrieved the answer but never used it.

Failure mode

A bi-encoder — the model behind fast vector search — embeds the query and each document separately. The two encodings never see each other, so there is no cross-attention between query terms and passage terms. The model can place a passage in the right neighbourhood but cannot judge fine-grained query↔passage interaction (negations, qualifiers, which entity the question actually asks about). Result: the best answer is retrieved, but ranked too low to make the context window.

02 How it works

The fix is a second model that scores relevance properly — but only over a tiny shortlist, because it is far too slow to run over the whole corpus. Two model shapes do the work:

Bi-encoder (the retriever)

Encodes the query and every document independently into vectors, then compares those vectors (cosine / dot product). Because document vectors are computed ahead of time and indexed, a query only needs one encode plus a nearest-neighbour lookup. Fast, scales to millions of documents — but approximate, because query and document never interact during scoring.

Cross-encoder reranker (the precise pass)

Feeds the query and a single passage together through one model that attends across both at once, then outputs a single precise relevance score. Because it sees every query token against every passage token, it captures the interactions a bi-encoder misses. Accurate — but too slow to run over the whole corpus: every (query, document) pair is a fresh forward pass, so cost grows with the number of candidates scored.

So the pattern is: retrieve top-N cheaply with the bi-encoder (e.g. N = 20–50), then rerank only those N with the cross-encoder and keep the top few for the context window. You pay the expensive model on dozens of candidates, not millions.

The reranker is pluggable. It can be a local cross-encoder running on your own hardware, or a hosted reranker such as Cohere or Voyage behind an API. LanceDB exposes a reranker step directly in its query pipeline, so the shortlist-then-rerank flow drops into the retrieval call.

corpus (millions) │ [ bi-encoder retrieval ] ← fast, approximate │ ▼ retrieve top-N (N = 20–50) │ [ cross-encoder rerank ] ← precise, attends query+passage together │ ▼ keep top-k (the context window)
The headline number

In Anthropic's benchmark, stacking reranking on top of contextual hybrid retrieval reached a 67% reduction in retrieval failures. The stack compounds: contextual embeddings −35% → adding contextual BM25 −49% → adding rerank −67%. Reranking delivers the largest single step in that chain — once hybrid and contextual retrieval are already in place.

04 Decision lens

When to reach for reranking — and when to skip it

✓ Reach for it when

  • Retrieval recall is decent, but the right passage often isn't in the top 3–5 — it's there, just ordered too low.
  • You can spend ~tens to hundreds of ms and a little cost per query reranking 20–50 candidates.
  • Answer quality is sensitive to precision — the generator only sees a few passages, so their order is load-bearing.
  • Hybrid + contextual retrieval are already in place — rerank gives the biggest cumulative failure reduction on top of them.

✕ Skip / overkill when

  • Your latency budget is razor-thin — a per-query rerank pass blows it.
  • Top-k is already near-perfect — measure first before adding a model that can only reorder.
  • Retrieval recall is so low the right doc isn't even in the top-N — fix retrieval first; rerank can only reorder what was retrieved.

Tradeoff: rerankers add per-query latency and (for hosted ones) cost, and both scale with N — so cap N. But because it delivers the biggest cumulative failure reduction in the stack, it's worth it once hybrid + contextual retrieval are in.

05 In Bergamot

task-31.4 ships the reranking stage of the retrieval pipeline:

  • A reranking stage that re-scores the top-N hybrid candidates before they reach the context window.
  • At least two reranker options benchmarked on the evaluation harness, with one chosen by measured ROI / cost rather than reputation.
  • Reranker choice and candidate count (N) are configurable, so the latency/precision tradeoff is tunable per deployment.
  • A measured improvement over hybrid-without-rerank on the harness — the layer has to earn its latency before it ships on by default.
