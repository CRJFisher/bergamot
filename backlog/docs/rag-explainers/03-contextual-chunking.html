Chunking & Contextual Retrieval

How to split a page so each piece is independently findable — and how to give every piece enough context to be understood on its own.

01 The problem

Bergamot's baseline retrieval embeds each re-downloaded public page as one vector. A whole page — sometimes thousands of words — is compressed into a single point in embedding space. Embedding means turning text into a fixed-length list of numbers (a vector) whose direction encodes meaning, so that similar texts land near each other. Retrieval is the step that, given a query vector, returns the stored vectors closest to it.

Failure mode

A whole-page vector is an averaged blur. The page covers ten topics, so its single vector sits in the bland middle of all of them. A query about one specific paragraph has to compete with the whole noisy page, and the signal it wants is diluted by everything else on the page. Long pages also exceed the granularity an embedding model can represent well — past a certain length the vector simply stops being faithful to any one passage.

The obvious fix is to cut the page into smaller pieces. But naive fixed-size chunking creates the opposite problem. Slice every 500 characters and you get a chunk like "It rose 3% over the prior quarter." — which has lost what "it" refers to and which quarter is meant. The chunk is now precise but contextless, so a relevant query can no longer match it.

So we are squeezed between two failures: chunks too big to be precise, or chunks too small to be self-explanatory. The techniques below resolve both.

02 How it works

Three ideas stack together. The first decides where to cut, the second restores lost context, and the third reunites a matched chunk with its full source.

1 · Structure-aware chunking

Instead of cutting at a blind, fixed character count, split along the document's own structure. Break on Markdown headers (#, ##), and within a section split recursively on paragraph and sentence boundaries until each piece is under a target size. Recursive here means: try the biggest natural boundary first (sections), and only fall back to smaller boundaries (paragraphs, then sentences) when a piece is still too large. The result is chunks that begin and end at meaningful seams — a heading and the prose under it travel together — rather than mid-sentence.

2 · Anthropic Contextual Retrieval

Structure-aware cuts still leave chunks that lean on the surrounding page for meaning. Contextual Retrieval fixes this directly. For each chunk, you send an LLM two things: the chunk and its full source document. The LLM writes a short situating context — 50–100 tokens describing what this specific chunk is about and where it sits in the document. That generated context is prepended to the chunk before the chunk is embedded, and before it goes into the BM25 keyword index. (BM25 is a classic lexical scoring function that ranks by exact term overlap — it is the keyword half of hybrid search.) The chunk now carries its own context into both the dense vector and the keyword index.

The payoff is measured. In Anthropic's benchmark, contextual embeddings alone cut top-20 retrieval failures by 35%; adding contextual BM25 on top reached a 49% reduction in Anthropic's benchmark.

chunk ──┐ ├──► LLM ──► "This chunk is from Acme Cloud's source ──┘ (writes Q2 2025 earnings summary…" (50–100 tok) document context) │ ▼ ┌─────────────────────────┐ │ situating context │ ← PREPENDED │ + original chunk text │ └─────────────────────────┘ │ │ ▼ ▼ embed (dense) BM25 (keyword) │ │ └──── hybrid index ────┘

Concretely, the chunk text changes like this before indexing:

# BEFORE — ambiguous, contextless
"Revenue increased 3% over the previous quarter,
 beating internal targets."

# AFTER — LLM situating context prepended
"This chunk is from Acme Cloud's Q2 2025 earnings
 summary, discussing cloud-segment revenue. Revenue
 increased 3% over the previous quarter, beating
 internal targets."

3 · Parent-document retrieval

Small chunks match precisely, but a small chunk is a thin thing to hand to the generating model — it may lack the surrounding detail needed to answer well. Parent-document retrieval separates the unit you match on from the unit you return: you index the small chunks for precise matching, but on a hit you return the full parent page so the model receives complete context. Bergamot stores the chunk→page link in DuckDB, so resolving a matched chunk back to its source page is a single lookup.

04 Decision lens

When to reach for it — and when to skip

✓ Reach for it when

  • Chunks are frequently ambiguous out of context — web articles, docs, anything full of pronouns and relative references ("it", "this quarter", "the above").
  • Precision matters and you are losing answers to averaged-blur whole-page vectors.
  • You can afford a one-time LLM pass over the corpus at ingest.

✕ Skip / overkill when

  • Documents are already short and self-contained — tweets, product titles, single-sentence FAQ entries. There is no context to restore.
  • You literally cannot run an LLM at ingest time (no budget, no API access, no batch window).

Tradeoff. Contextual prefixing costs one LLM call per chunk at ingest — one-time, not per query — plus a re-embed of the contextualized text. Anthropic notes that prompt caching (the source document is cached and reused across all of its chunks) makes this pass cheap. Structure-aware chunking, by contrast, is nearly free. This is the single highest-ROI retrieval-quality upgrade in the plan, which is why it sits right after hybrid search.

05 In Bergamot

task-31.3 ships the full stack:

  • Re-downloaded public pages are split into structure-aware chunks instead of being embedded whole.
  • Each chunk is embedded and BM25-indexed with a 50–100 token LLM situating context prepended.
  • DuckDB stores the chunk→page linkage, so a hit returns its parent page for complete context.
  • The corpus is re-embedded, and the retrieval-failure reduction versus the whole-page baseline is measured on the harness.

The contextual-BM25 half pairs with the hybrid index from task-31.2 — the situating context lands in both the dense vectors and the keyword index, so both halves of hybrid search benefit at once.
