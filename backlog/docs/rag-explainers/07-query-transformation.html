Query transformation: rewrite the question before you search

The text you embed for retrieval need not be the text the user typed. Three optional transforms — HyDE, multi-query, and routing — reshape a raw query into something that matches your documents better, or decide it should skip retrieval entirely.

01 The problem

Bergamot's baseline retriever embeds the user's raw query verbatim: it takes whatever string the user typed, runs it through the embedding model, and ranks pages by cosine similarity against their vectors. That works when the query already reads like the answer. It works poorly when it does not.

An embedding maps text to a point in a high-dimensional vector space where nearby points mean similar things. The trouble is that a question and its answer are written in different registers — different lengths, vocabulary, and shape — so they often land far apart even when one perfectly answers the other.

Failure mode

There is a query–document asymmetry. A short keyword query like react hooks deps lives in a different region of embedding space than the verbose answer passages that actually contain the answer — paragraphs full of words like "the dependency array tells useEffect when to re-run the effect…". Embedding the bare query therefore retrieves weakly: the nearest vectors are other short, keyword-shaped snippets, not the long explanatory passages you want.

The same asymmetry makes vague or multi-part queries retrieve a muddle. A question that blends two intents ("how do hooks work and when do they re-run?") produces one averaged vector that sits between both topics and matches neither sharply.

02 How it works

Three independent techniques attack the asymmetry from different angles. All three are optional, gated by config, and only enabled by default if they actually pay off on the evaluation harness.

1. HyDE — Hypothetical Document Embeddings

HyDE bridges the gap by making the query look like an answer before embedding it. You ask a language model to write a hypothetical answer to the query — a short passage that could be the document you are looking for — and then you embed that hypothetical document instead of the bare query. You retrieve real documents that sit near this fake answer in embedding space.

The fake answer is allowed to be factually wrong; what matters is its shape. Because it is written in the verbose, explanatory register of a real passage, it occupies the same region of embedding space as the true answer passages — so it bridges the asymmetry that the bare query could not. HyDE is zero-shot: it needs no labelled query–document pairs to train on. Despite that, it is comparable to fine-tuned retrievers and outperforms an unsupervised dense baseline across tasks and languages.

query: "how do react hooks deps work?" | [ HyDE: LLM writes a hypothetical answer ] | v "The dependency array of useEffect lists the values the effect reads; React re-runs the effect whenever one of them changes between renders..." (hypothetical document) | embed (embed the hypothetical answer, NOT the bare query) | retrieve real docs nearest the hypothetical answer | v ranked results that now match answer-shaped text

2. Multi-query — fan out, then union

Multi-query expands one query into several paraphrases or sub-questions, retrieves for each variant independently, and then unions and de-duplicates the result sets. A single phrasing has one blind spot; several phrasings cover more of the answer's vocabulary, so a document missed by the original wording can still be caught by a paraphrase. This mainly improves recall on vague queries — the kind that one averaged vector matches poorly.

3. Routing — decide whether to retrieve at all

Routing puts a cheap classifier in front of retrieval to decide whether retrieval is even needed. A general-knowledge or arithmetic question — "what is 2+2", "who wrote Hamlet" — has its answer in the model's own weights and should not hit the knowledge base; retrieving for it only adds latency and the risk of injecting irrelevant passages. A question about the user's own captured content — "summarize the article I read about hooks" — clearly should retrieve. The router sends each query down the right path.

04 Decision lens

When to transform the query

✓ Reach for it when

  • Queries are short, vague, or keyword-y while documents are verbose — HyDE rewrites the query into answer-shaped text and closes the asymmetry.
  • Recall on ambiguous queries is weak — multi-query fans the question into paraphrases and unions the hits.
  • You want to avoid pointless retrievals on general-knowledge or arithmetic questions — a router answers them directly.

✕ Skip / overkill when

  • Queries are already well-formed and specific — they match documents fine on their own.
  • Latency or cost is tight: every transform adds an LLM call before retrieval even begins.
  • Measurement on the harness shows no marginal gain from the transform.

Tradeoff: each technique adds a pre-retrieval LLM round-trip (latency + cost), and each can introduce drift — a bad hypothetical document retrieves worse than the bare query, and a bad paraphrase pulls in noise. So keep every transform behind a config toggle and only default-on what the harness proves. This is precisely why query transformation is sequenced late in the roadmap and marked optional: it is an upgrade you switch on once you can measure that it helps, not a foundation you build on.

05 In Bergamot

task-31.7 ships all three transforms as measured, toggle-gated options:

  • HyDE behind a config toggle: an LLM writes a hypothetical answer, and that document — not the bare query — is embedded for retrieval.
  • Multi-query expansion behind a toggle: the query is fanned into paraphrases, each is retrieved, and the results are unioned and de-duplicated.
  • A router that decides whether retrieval is needed at all, so general-knowledge and arithmetic questions skip the knowledge base.
  • Each technique's marginal gain is measured on the harness from task-31.1, and the default for each toggle is set by the result — on by default only where it demonstrably helps.
