Phase D · task-31.2 · Hybrid

Hybrid search: dense meaning + BM25 keywords, fused with RRF

Dense retrieval understands what you mean; keyword retrieval finds the exact tokens you typed. Each is blind where the other sees. Hybrid search runs both lanes and fuses their rankings so a single query is rescued by whichever modality has the answer.

01 The problem

Today, Bergamot's baseline retriever embeds each re-downloaded public page as a single dense vector — one embedding for the whole page — and stores it in LanceDB. At query time it embeds the query and ranks pages by cosine similarity against those vectors. That is the entire retrieval path: pure dense, no keyword search.

Dense vectors are wonderful at meaning. They are weak at surface form. An embedding compresses a passage into a few hundred dimensions of "aboutness," and in doing so it blurs the exact tokens — the precise spelling of a rare API name, an error code, a product ID, an acronym. Two strings that look almost identical to a human can land far apart in embedding space, and a query for one literal token may retrieve "semantically nearby" pages that never contain it.

Failure mode

Pure dense retrieval misses exact-term queries. Search for ECONNREFUSED, a function name like useDeferredValue, an order ID, or an acronym, and dense retrieval often floats up topically-related pages while the one page that literally contains the token sinks — because embeddings smear those rare surface tokens away.

Pure keyword retrieval misses paraphrases. A lexical engine matching why does my server connection keep dropping finds nothing if the right page says "the socket is reset by the upstream host" — no shared words, even though it is the answer.

Each modality alone has a blind spot. The fix is not to pick one; it is to run both and combine their results.

02 How it works

Two kinds of retrieval

Dense retrieval. An embedding model maps text to a vector. The query is embedded the same way, and documents are ranked by cosine similarity between vectors. Because the vectors encode meaning, dense retrieval captures paraphrase and synonymy: "connection dropping" can match "socket reset" even with zero shared words.

Sparse / BM25 retrieval. A keyword index scores documents by term frequency — how often the query's words appear in a document, damped by how common each word is across the corpus and by document length. This is lexical, exact-token matching: it nails rare names, codes, and acronyms that appear verbatim, but it cannot bridge a paraphrase because it only knows the words it was given. BM25 ("Best Matching 25") is the standard scoring function for this lane.

Fusing two ranked lists: Reciprocal Rank Fusion

The two lanes produce two ranked lists with incomparable scores — a cosine similarity and a BM25 score live on different scales, so you cannot just add them. Reciprocal Rank Fusion (RRF) sidesteps this by ignoring the raw scores entirely and combining ranks. Each document earns, from each list, a contribution of 1 / (k + rank), and its fused score is the sum across lists: 

# Reciprocal Rank Fusion — rank-based, no score calibration needed
score(d) = Σlists  1 / (k + ranklist(d))

# rank starts at 1 for the top hit in each list
# k is a smoothing constant; default k ≈ 60
# a doc ranked #1 in a list contributes 1/(60+1) = 0.0164
# a doc ranked #5 contributes               1/(60+5) = 0.0154

Because RRF only reads each document's position, it needs no score calibration between the lanes — a cosine of 0.83 and a BM25 of 14.2 never have to be reconciled. The constant k (default ≈60) softens the gap between top ranks: a larger k flattens the curve so deeper-ranked documents contribute almost as much as top ones; a smaller k sharpens the reward for being #1.

LanceDB supports hybrid search natively in its embedded TypeScript SDK. It runs a dense vector query alongside a full-text / BM25 index built on Tantivy, then merges the two result sets. Its default fusion is RRFReranker() — exactly the formula above. Anthropic, in its contextual retrieval work, reports starting from a weighting around 0.8 semantic / 0.2 BM25 when blending the lanes, which is a sensible default to tune from.

04 Decision lens

When to reach for hybrid search

✓ Reach for it when

  • Your corpus is full of names, codes, jargon — web content, technical docs, source code — and users also ask in paraphrase.
  • You need to retrieve exact tokens (API names, error codes, product IDs, acronyms) that dense vectors blur away.
  • Your vector store supports it natively — LanceDB does — so the second lane is nearly free to add.

✕ Skip / overkill when

  • Your content is purely conversational or semantic with no exact-match needs — BM25 adds noise, not signal.
  • Your store has no FTS support, so you'd have to stand up and operate a second search engine solely for this one lane.

Tradeoff: you pay a tiny indexing + fusion cost — one extra FTS index and one more query lane per search. On a stack where the vector store already supports it, this is essentially the highest ROI-per-effort retrieval upgrade available, which is why it is sequenced right after the evaluation harness: cheap to ship, measurably better.

05 In Bergamot

task-31.2 ships hybrid retrieval on the existing LanceDB stack:

  • A BM25 / full-text index is built alongside the dense vector index in the same LanceDB table — no second engine.
  • semantic_search issues a hybrid query — dense lane plus BM25 lane — fused with RRF through the LanceDB TypeScript SDK.
  • The semantic-vs-BM25 weighting is configurable (starting near 0.8 / 0.2, per Anthropic's guidance) so it can be tuned per corpus.
  • On the evaluation harness from task-31.1, hybrid retrieval beats the pure-dense baseline — the gain is measured, not assumed.
