Time-aware retrieval: the recency signal Bergamot already captures

A browsing corpus is intrinsically temporal — every page you visit is timestamped. Yet semantic (and even hybrid) search is blind to when you saw something, so "what was I reading last month about X" and "the latest thing I saw on Y" both fail. Time-aware retrieval makes recency a first-class signal — carefully, so it lifts the relevant-and-recent page without letting freshness drown relevance.

A note on the name

The prompt for this work was "Temporal Cluster RAG" — but that is not an established technique (it traces to a single uncited blog post). It is an informal composite of two separable capabilities: time-aware retrieval (this page — cheap, proven, shipping as task-31.11) and temporal topic clustering (Topic Detection & Tracking — heavier and speculative, deliberately deferred). We adopt the named, cited halves, not the coinage.

01 The problem

Bergamot's retriever ranks captured pages by cosine similarity to the query — and after task-31.2, by a hybrid of dense + BM25. Both score aboutness and nothing else. A page you visited this morning and one you visited eight months ago compete on identical footing. For a personal knowledge manager built on a browsing timeline, that throws away the signal users reach for most often: time.

Failure mode — and the trap on the other side

Time-blind retrieval can't answer time-intent queries. "The article I read last week about async runtimes" returns the most topically similar page even if it's a year old; "the latest benchmarks" can't prefer the newest of several relevant hits. In one study a cosine-only ranker scored 0.00 on "latest"-style tasks.

But a naive recency boost is worse. Multiply every score by "newness" and you surface whatever you happened to browse recently — the espresso-machine review you read at lunch outranks the relevant article from last month. Push the recency weight too high and accuracy collapses (to ~0.667 in the same study). Crank time-decay hard enough and a durable reference page becomes unretrievable past an age horizon no matter how relevant — the event-horizon problem.

The signal is real; the danger is letting it overpower relevance. The fix is to add time conditionally and bounded, never as a blanket multiplier.

02 How it works

Step 1 — detect time intent, then pre-filter

Most queries have no time intent ("how does TCP backoff work?") — leave those alone. When a query carries an explicit or relative time expression — "last month", "recently", a date range — anchor it to a reference "now" and convert it to a concrete timestamp window, then apply a hard pre-filter (WHERE on the visit time) before semantic ranking. A pre-filter is a precise binary gate: it is cheaper and less error-prone than trying to express "only last month" as a soft score, and it cannot accidentally surface an out-of-window page.

Step 2 — an optional, bounded recency rerank

When recency should influence order rather than gate it, rerank the candidates with a convex combination of relevance and an exponential decay on page age: 

# Convex combination — relevance and recency on one [0,1] scale
score(d) = α · cos(d)  +  (1 − α) · 0.5(age_days(d) / half_life)

# cos(d)      relevance, already in [0,1]
# 0.5^(age/H) recency: 1.0 today, 0.5 at one half-life H, 0.25 at 2H ...
# α ≈ 0.70   weight on relevance (tune on the harness)
# both terms bounded => recency can nudge, never dominate outright

Because both terms live on the same [0,1] scale and are added (not multiplied), recency lifts a page's score but can never zero it out — that is what sidesteps the event-horizon trap a pure multiplicative decay falls into.

Step 3 — gate the boost behind a relevance floor

The one rule that keeps recency honest: apply a raw-cosine relevance floor. A page whose cosine is below the floor (≈ 0.35–0.50 for dense embeddings, calibrated on your own model) is never eligible for a recency boost — so a fresh-but-off-topic page cannot climb. Recency reorders the relevant set; it does not admit the irrelevant.

None of this needs new infrastructure. Bergamot already stores page_loaded_at and captured_at per visit and already has an index on page_loaded_at, so the pre-filter is cheap and the decay is a few lines over data that is already there.

04 Decision lens

When to reach for time-aware retrieval

✓ Reach for it when

  • Your content has a strong time dimension and users ask relative-time questions — a personal browsing KM is the canonical case.
  • You already store timestamps (Bergamot does), so it is a scoring change, not new infrastructure.
  • You can detect intent and gate the recency boost — apply it conditionally, never globally.

✕ Skip / overkill when

  • Queries are timeless reference lookups ("how does X work") — recency is noise there, so leave those untouched.
  • You'd apply a fixed global decay with no relevance floor — that regresses quality by surfacing fresh-but-irrelevant pages.
  • You're tempted by learned per-query gating or embedding-level time fusion before measuring — that's the deferred ceiling, not the baseline.

Tradeoff: the pre-filter is a precise binary gate (loses fine ordering inside the window); the decay is a smooth gradient (needs an α / half-life tune). Both are cheap and run over an index that already exists — which is why this is sequenced as a high-ROI add once hybrid search and the harness are in place. Heavier variants — learned gating (Re3), embedding-level timestamp fusion (TempRetriever), and temporal-knowledge-graph RAG (TG-RAG) — are deferred until a measurement asks for them.

05 In Bergamot

task-31.11 adds the time signal on top of the hybrid pipeline (task-31.2), over data Bergamot already captures — no schema change:

  • semantic_search gains an optional time_range, applied as a pre-filter on page_loaded_at (using the existing index) before semantic ranking.
  • Relative expressions ("last month", "recently") are anchored to a reference now and converted to a concrete timestamp range.
  • An optional recency rerank blends cosine with a configurable α and half-life, gated by a raw-cosine relevance floor calibrated to Bergamot's embedding model.
  • Time weighting fires only on detected intent, never as a fixed global decay; missing/garbled timestamps degrade gracefully to "no time signal".
  • On the task-31.1 harness, time-intent queries improve over the hybrid baseline with no regression on timeless queries — the gain is measured, not assumed.

This is the cheap, proven half of the original "time + topic clusters over time" idea. Its sibling — temporal topic clustering (an offline job that clusters stored vectors over Bergamot's navigation-tree / activity-session windows and tracks evolving themes) — is genuinely useful but needs new batch infrastructure and has unproven value at personal scale, so it is recorded as a deferred architecture with a concrete revisit trigger rather than built now.
