Trigger & off-thread orchestration

Task 36.9 wires the windowed HDBSCAN clustering run behind two entry surfaces and keeps every heavy stage — re-download, embedding, and the multi-second fit — off the extension-host event loop, so a run never freezes the UI or stalls the /visit capture endpoint.

command · bergamot.tdt.rebuildClusters scheduler · default 24h compute · forked child process DB writers · exactly 1 status · Done

00The whole run, at a glance

Both entry surfaces funnel through one single-flight guard into the same pure orchestrator, rebuild_clusters(deps, spec). The orchestrator prepares vectors and visits, splits the range into calendar windows, and for each window either memoizes away the work or dispatches the fit to a forked worker before the single DuckDB writer persists the result.

pure core

Dependency-injected

The orchestrator imports no vscode, no DuckDB, and no clustering-tfjs values — fakes drive it in unit tests; production injects the real reader, worker client, and sink.

passive

Runs itself

The scheduler surfaces projects without the user remembering to trigger anything; a quiet day costs ~nothing thanks to fingerprint idempotency.

single writer

One DB handle

The forked worker never opens DuckDB. All writes go through the extension's one handle via ClusterStore (plan §3).

01Two entry surfaces, one guard

A run starts one of two ways: the user invokes the manual command, or the in-host scheduler ticks. Both call server_manager.rebuild_clusters(spec), which wraps the work in a single_flight() latch — if the scheduler fires while a manual run is live, the tick joins the in-flight promise instead of starting a second run.

manual

bergamot.tdt.rebuildClusters

Registered in command_manager.ts. Wraps the run in a progress notification and reports a result message (windows clustered, visits read, origins excluded). On-demand and the testing path.

automatic

ClusterScheduler

An in-host VS Code timer — not OS cron. First tick 60s after activation; then every tdt.clusterCadenceHours (default 24, 0 disables). Re-arms only after a tick settles.

Why an in-host timer, not OS cron

An OS cron job would need its own headless writer, violating the single-writer model (plan §3). The trigger lives inside the one process that owns the database. A floor of 1 hour (MIN_CADENCE_MS) stops a misconfigured tiny cadence from busy-looping the re-download.

The scheduler's self-re-arming tick (cluster_scheduler.ts)

Each tick runs in a try/finally: a run error is surfaced via on_error but never kills the schedule, and the next tick is armed only in finally — after the current one settles — so the scheduler can never overlap itself.

vscode/src/tdt/cluster_scheduler.ts · tick()
private async tick(): Promise<void> {
  try {
    await this.options.run(default_window_spec(this.options.now()));
  } catch (error) {
    this.options.on_error?.(error);  // a run error must not kill the schedule
  } finally {
    const hours = this.options.cadence_hours();
    if (hours > 0) {
      this.arm(Math.max(MIN_CADENCE_MS, hours * 60 * 60 * 1000));
    }
  }
}

02The default window spec

Both surfaces cluster the same default range: the start of the previous calendar month → now. The closed previous month re-runs once more to pick up late-arriving visits and then becomes a no-op; the open current month re-clusters as visits accumulate.

vscode/src/tdt/rebuild_clusters.ts · default_window_spec()
export function default_window_spec(now: Date): WindowSpec {
  const range_start = new Date(
    Date.UTC(now.getUTCFullYear(), now.getUTCMonth() - 1, 1, 0, 0, 0, 0),
  );
  return { range_start: range_start.toISOString(), range_end: now.toISOString() };
}

03Inside the orchestrator pipeline

rebuild_clusters(deps, spec) runs five sequential stages before the per-window loop. The first three prepare a clean, vectorised, origin-filtered visit set; windowing then subdivides the range into the units that actually get clustered.

Stage 2 — why vectorise is "off the event loop"

The embed pass never blocks the JS thread: ONNX inference runs on libuv's threadpool, fetches are async I/O, and a setImmediate yield between pages lets /visit capture interleave. Never-cluster origins are dropped before re-download. An embed_pass_flight single-flight prevents two concurrent passes.

Stage 3 — the visit read cap (and why it sits above max_samples)

MAX_VISITS_IN_WINDOW = 5000 caps the bulk read of a full window. The cap deliberately sits above max_samples: a heavy month must be read in full so windowing can subdivide it — capping at max_samples would drop the very pages subdivision exists to separate. A cap-hit is logged as a possible truncation; nothing is silently dropped.

Stages 1 & 4 — never-cluster origin exclusion (rebuild_clusters.ts)
vscode/src/tdt/rebuild_clusters.ts · the filter
const never_origins = await deps.list_never_cluster_origins();

04The per-window decision tree

Each WindowSignal resolves to exactly one of four statuses. Three of them exit before any worker spawns — most importantly the fingerprint match (unchanged), which is what makes a quiet-day scheduled tick almost free.

clustered unchanged skipped_sparse skipped_no_vectors
The idempotency no-op

The input_fingerprint is computed identically to the value stored on the live run, so an equal value means the window's inputs are byte-for-byte unchanged. On a match the orchestrator returns unchanged immediately — the heavy worker never forks and nothing is written. This is the §6 memoization that makes daily ticks cheap.

The fingerprint probe (rebuild_clusters.ts · run_one_window)
vscode/src/tdt/rebuild_clusters.ts · §6 memoization
const fingerprint = compute_input_fingerprint(
  kept_visits.map((v, i) => ({
    page_session_id: v.page_session_id,
    embedding_vector_version: vector_versions[i],
  })),
);
const existing = await deps.live_run_fingerprint(window_start, window_end, params_hash);
if (existing === fingerprint) {
  return { ...signal, status: "unchanged", persist: null }; // no re-fit, no persist
}

const output = await deps.compute({ // forks the worker
  visits: kept_visits, vectors, hdbscan: deps.hdbscan_config,
  max_samples: deps.window_config.max_samples,
});

Memoization key: matched on (window, params_hash, embedding_model_id) but not algo_version — the host cannot resolve algo_version without loading TensorFlow. A pure backend change therefore re-clusters a window only when its inputs next change.

05The clustering worker — off-thread compute

When a window must cluster, the dense O(n²) cosine build and HDBSCAN fit run in a forked child process (mirroring the MCP-server spawn pattern). The host driver ships one window's input over IPC and kills the one-shot child as soon as the result returns.

vscode/src/tdt/cluster_worker_client.ts · run_cluster_compute()
const child = child_process.fork(options.worker_path, [], {
  // the host binary run as node (a packaged install has no `node` on PATH)
  execPath: process.execPath,
  env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" },
  // structured clone so Float32Array vectors survive IPC intact
  serialization: "advanced",
});

const timer = setTimeout(() => finish(() => reject(...)), DEFAULT_TIMEOUT_MS); // 10 min

child.on("message", (m: ClusterWorkerResponse) => {
  if (m.ok) finish(() => resolve(m.output));
  else finish(() => reject(new Error(`cluster worker failed: ${m.error}`)));
});
// finish() is idempotent: clears the timer, kills the child, settles once —
// on message, timeout, 'error', or an unexpected early 'exit'.
vscode/src/tdt/cluster_worker.ts · the forked entry point
import { compute_clusters } from "@bergamot/tdt/out/cluster_pipeline";

async function handle(message: ClusterWorkerRequest): Promise<void> {
  try {
    const output = await compute_clusters(message.input); // the only clustering-tfjs call site
    send({ ok: true, output });
  } catch (error) {
    send({ ok: false, error: error instanceof Error ? error.message : String(error) });
  }
}
process.on("message", (m: ClusterWorkerRequest) => { void handle(m); });
// touches NO DuckDB and NO vscode APIs — it can never contend for the single writer
DecisionWhy
Forked process, not worker threadMirrors the two existing spawn precedents (MCP server, browser provisioner) and gives the native TensorFlow backend a clean process.
serialization: 'advanced'Structured clone so Float32Array page + representative vectors cross IPC as typed arrays, not JSON-mangled plain objects.
One-shot, killed after resultNo idle child leaks; the model and TF backend it loaded are released with the process.
Re-download stays in-hostA worker cannot hold the single-writer DuckDB it would need to read the corpus and write vectors through; off-the-event-loop is achieved inside the embed pass instead.
Settle-exactly-once footgun

A broken IPC channel makes child.send() throw synchronously, outside the 'error' event. The driver wraps the send in try/catch so a failed send still settles via finish() — otherwise it would leak the armed timer and an un-killed child.

06ClusterStore persist — three outcomes

ClusterStore.persist(bundle) performs an atomic read-decide-write against topic_run / topic_cluster / topic_cluster_member. The decision branches on whether a run with this run_id already exists and whether its input_fingerprint matches.

no-op

Unchanged

A complete run with this run_id and matching input_fingerprint already exists. The table is left untouched.

replace

Atomic replace

Same run_id, different fingerprint (re-embedding or late visits). Old clusters/members are deleted and new ones inserted in one transaction; created_at is preserved.

create

Create + supersede

No run with this run_id (model/params/algo changed → new id). The new run is inserted as complete and any other complete run for the window is marked superseded. History is retained.

Soft references, not foreign keys

Cross-table references between topic_run, topic_cluster, and topic_cluster_member are soft (no FK) because DuckDB cannot cascade-delete within one transaction — the replace path deletes members and clusters explicitly. No DB constraint enforces "one live run per window"; the supersede step upholds it per branch.

07Extension activation & deactivation

Activation initializes the encrypted DuckDB, builds the ServerManager (passing extension_path so it can locate out/tdt/cluster_worker.js), registers commands, and starts the scheduler. Deactivation disposes the scheduler first, before the DB closes, so no pending tick fires into a torn-down writer.

Deactivation ordering matters

cluster_scheduler.dispose() clears the pending setTimeout and sets a disposed flag so no further tick can be armed. Doing this before close_all() guarantees a scheduled run never starts writing into a closing database.

Lazy imports — keeping TensorFlow out of activation

rebuild_clusters.ts, cluster_worker_client.ts, the cluster/vector stores, and the whole TensorFlow chain are dynamically import()-ed inside server_manager.rebuild_clusters() — so the clustering-tfjs chain only ever loads in the forked worker, never eagerly on extension activation.

08Key architectural constraints

Five invariants hold across every run. They are the reasons the design looks the way it does.

single writer

One DuckDB writer

The clustering worker never opens DuckDB. All writes go through the extension's single handle via ClusterStore. The worker returns raw results for the parent to persist.

privacy

Never-cluster origins, three levels

Excluded (a) before re-download in the embed-pass corpus, (b) from the clustering input filter, and (c) implicitly from the vector read — they have no vectors.

idempotency

Quiet days are free

A daily tick over an unchanged window matches its fingerprint → no worker spawn, no DB write. Cost is bounded by §8 idempotency.

memoization key

Window + params + model

The live-run probe matches on those three, not algo_version (the host can't resolve it without TensorFlow). A pure backend change re-clusters when inputs next change.

lazy load

No eager TensorFlow

The orchestrator, worker client, and TF chain are dynamically imported inside server_manager.rebuild_clusters(), so they never load on activation.

resilience

Failures clear the latch

The single_flight latch clears on settle — success or failure — so a failed run never permanently wedges future runs.
