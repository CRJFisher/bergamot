Five things a person wants — and the exact path to each

5 user flows 2 users · 5 flows olive works · clay friction · rust blocked

The Surface Map graded the four doors in the abstract. This page follows two real people through them. User A drives Claude Code as a research agent and thinks in prompts and skill calls. User B keeps a markdown notes vault in VS Code and wants their browsing to feed their notes. Each of the five flows below starts from something a person actually wants — "what have I been researching this week?", "I'm writing a note on topic X, what have I browsed?", "turn this browsing cluster into a note", "this cluster is wrong, fix it", "did the rebuild even run?" — and traces the exact path of surfaces, commands, and routes they'd have to string together to get there. Green steps work today. Where a step forces a workaround, has no surface at all, or silently fails, the path is marked with the pain point in plain terms.

Works with friction

User A or User B — the hero loop: read a cluster, stage a stub

step works workaround / dead-end pain point
  1. 1
    cluster --id <id> reads the detailserver_manager.ts :588-595

    Pulls the cluster's exemplar and member pages (with live URLs) so the agent has real material to summarise.

  2. 2
    stub --id <id> drafts the notebergamot-clusters/SKILL.md :49-60

    The agent composes a one-line summary, then stub writes a promotable Map-of-Content stub. Idempotent: re-running overwrites its own un-promoted draft only.

  3. 3
    POST /stage_cluster writes the fileserver_manager.ts :634-654

    The single writer lands the draft in bergamot.staging/ so the forget-sweep and ledger stay in one place. A 409 tells the user to refresh if the cluster recomputed away.

  4. 4
    Path from staged stub to vault note is opaque pain pointUX Gap 7 · no follow-through

    Bergamot never writes into canonical notes (constitution principle 8) — the user must review and promote by hand. But nothing shows the file arrived or how to promote it, so the loop feels like it stops at a directory.

Blocked · no signal

User A or User B — wants a last-build time or staleness signal

step works workaround / dead-end pain point
  1. 1
    User wants a last-build time or staleness signalUX Gap 4 · freshness

    A passive "your clusters were rebuilt N hours ago" cue — the ordinary trust signal that the background job is alive.

  2. 2
    Only coverage or a manual rebuild existcommand_manager.ts :48-75

    coverage --days 7 gives per-window stats, not a last-run time; rebuildClusters forces a run (with a progress notification) but that is triggering work, not checking on it.

  3. 3

    Each tick re-arms the next; on failure it calls on_error — "a run error must not kill the schedule" — which only logs to the Output panel. Nothing surfaces success, last-run time, or staleness anywhere the user looks.

Two blockers underneath every flow

These are not per-flow bugs — they are structural, and they recur across the five paths above.

Recurring · structural

Cluster ids are ephemeral

Every id rotates on recompute, so nothing a user sees can be referenced next session. Discovery lists (a), the hero loop's target (c), and curation's target id (d) all break the moment clustering re-fits.

Recurring · structural

There is no passive / IDE surface

Clusters live nowhere the user passively looks. Every flow — discovery, note context, curation, freshness — drops to the CLI/skill because there is no panel, no editor affordance, and no ambient signal in VS Code.
