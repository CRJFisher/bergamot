📝 Page Processing

How a captured page becomes a stored record. Moving from an LLM categoriser that runs up to four model calls per page to a deterministic essence-capture pipeline with a single cheap Haiku call — usage-agnostic by design.

capture → extract (non-LLM) → gate → summarize (1× Haiku) → store essence

Page processing is the stage inside the VS Code extension that turns a captured page into a durable record. The redesign has one organising idea: capture the essence of a page deterministically, and store it in a form that is agnostic to how it will later be used. Classification work shrinks to a single deterministic gate, content extraction moves off the LLM entirely, and exactly one cheap model call writes a short summary. This page describes the target design (task-35); the "before" is shown for contrast only.

  • Overlapping work: classify, content-processing and analysis all re-read the same page from scratch.
  • No real extraction: reduce_html_for_llm only strips obvious noise; it never isolates the article, so the LLM does the extraction over up to 100k chars — the dominant token cost.
  • Usage-specific storage: intentions / tree_intentions guess why the user viewed a page — an interpretation baked into the capture record.
  • The one expensive call: tree-intentions runs on sonnet and re-derives intentions across the whole visit tree.

3Target pipeline

Deterministic extraction is the core. A real content extractor isolates the article and hands back clean markdown plus title, excerpt, author, site, published date, word-count, language and lead image — for free, with no model call. A deterministic gate decides keep/drop from those signals. Only kept pages pay for a single Haiku call that writes a short summary and topic labels.

Non-LLM extraction

Defuddle (via defuddle/node) with linkedom as the DOM provider isolates the main article and emits markdown + rich metadata. Readability + turndown is the all-CJS fallback if the ESM-in-CJS integration proves fragile.

Deterministic gate

No taxonomy, no model. The extractor's "no article found" signal — empty body, low word-count, high link-density — decides keep/drop. Dropped pages cost zero LLM calls. PDFs / non-HTML get a dedicated drop reason.

One Haiku call

Over already-clean text, a single call returns {summary, topics}. On failure or non-JSON it falls back to the extractor's free excerpt and records the stage + a snippet — it never crashes the workflow.

Structural tree only

Navigation trees are built from referrer / tree_id relations — independent of intentions. They keep working with the intention fields gone.

4The stored record — PageEssence

One canonical, usage-agnostic record replaces webpage_analysis. It describes what is on the page, not what the page was for — so any downstream consumer (browsing, RAG, future query-time intent derivation) reads the same shape. The full markdown is stored durably in DuckDB (webpage_essence.markdown), keyed by page_session_id — so when RAG chunking (task-31.3) later replaces the whole-page LanceDB record with chunk records, parent-document retrieval still has a durable full-page source and a stable chunk↔page id.

PageEssence — DuckDB webpage_essence is the durable source of truth; LanceDB webpage_content is the embedding copy

  • DuckDB webpage_essence (source of truth): page_session_id (PK) · markdown · title · summary · topics(JSON) · author · site_name · published_at · word_count · lang · lead_image_url. (replaces webpage_analysis; the intentions column and the misspelled page_sesssion_id are gone.)
  • LanceDB webpage_content (embedding copy): {page_session_id, pageContent: markdown, url, title, summary, topics, word_count} — embedded with local all-MiniLM-L6-v2 (384-dim). page_session_id + word_count ride along so citations and the task-31.8 small-corpus budget need no extra DuckDB round-trip.
  • Removed: the webpage_tree_intentions table and the entire tree-intentions step.

5Default model & cost

Haiku is already what most calls use today (Claude provider, fast role). The redesign makes it the explicit, configurable default and deletes the only sonnet call, so per-page cost collapses to one small call over clean text.

Configurable default

bergamot.models.fast / bergamot.models.smart override the built-in role→model maps. Unset = byte-identical to today (fast → haiku). The smart role is retained but currently has no caller.

Cost shape

Stored page: 4 → 1 calls, and the survivor runs over a few KB of clean markdown rather than up to 100k chars of raw HTML. Dropped page: → 0 calls. The sonnet spend is gone entirely.

Proven, not assumed

A light ~20–30 page golden set asserts extraction coverage and Haiku summary acceptability (deterministic keyword-overlap) and records a before/after tokens-per-page figure — without building a heavyweight F1 / RAGAS harness.

6Information-architecture remodel

With classification shrunk and "capture the essence" as the core, the modules are renamed to say what they are, and the stateless WebpageWorkflow class dissolves into composable functions (the repo forbids stateful classes). Pure renames land as a final, rename-only PR for reviewability.
