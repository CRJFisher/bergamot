📥 Page Processing

How a captured page becomes a stored record. Ingestion is pure, lossless capture with zero LLM calls: the raw page is stored compressed alongside cheap metadata, and all interpretation (extraction, chunking, embedding, summarisation) belongs to the RAG-prep pipeline.

visit → deterministic gate → store raw page + metadata  ·  (no LLM, no network)

Page processing is the stage inside the VS Code extension that turns a captured page into a durable record. The organising idea is to separate capture from interpretation. Capture is deterministic and lossless — it persists the raw page bytes (zstd-compressed) and a little cheap metadata read from the document <head>, and makes no LLM calls at all. Everything interpretive — isolating the article, chunking, embedding, summarising — is the job of the RAG-prep pipeline (task-31), which reads the stored raw pages on its own schedule and can re-run over the whole corpus with better algorithms.

Why store the whole page? A page can never be re-captured — once you have left it, lossy extraction at ingest is an irreversible loss. Storing the raw page (zstd-compressed, a few hundred KB) is cheap and lets the RAG pipeline re-extract and re-chunk the entire corpus at any time. Capture preserves; the pipeline interprets.

1The capture pipeline

Capture is a short, fully deterministic path orchestrated by run_page_capture(deps, inputs) in vscode/src/workflow/page_capture_pipeline.ts — a plain function over an immutable CaptureDeps struct, not a stateful class. For each visit it runs the relevance gate; for kept pages it stores the raw page compressed together with cheap <head> metadata. No model is ever called and nothing is written to a vector store.

Navigation-tree linking (referrer → tree) happens upstream in the visit queue (webpage_tree.ts) before the pipeline runs, and is independent of the keep/drop decision — every visit gets a tree node; only the capture is gated.

Lossless capture

The raw page is stored zstd-compressed in DuckDB. Nothing is interpreted or thrown away, so the RAG pipeline can re-extract and re-chunk the whole corpus later with better algorithms.

Cheap metadata only

Title, site, author, published date and language come straight from the HTML <head> / Open-Graph tags — a trivial regex parse (read_metadata.ts), not main-content extraction. Enough to browse and to title navigation-tree nodes.

Zero LLM, zero failure surface

Ingestion makes no network call and cannot fail on auth, prompt-length, or non-JSON. It is the cheapest, most robust path; all model cost lives in the RAG pipeline where it is gated.

2The relevance gate

evaluate_page_gate(raw_page, url) (vscode/src/workflow/page_gate.ts) returns a GateDecision {keep, reason} from cheap, deterministic signals — no LLM, no topic taxonomy, no main-content extraction. It is deliberately permissive: capture is cheap and lossless, and quality/topic filtering belongs to the RAG-prep pipeline, so the gate keeps essentially everything and drops only transient interstitials that carry no durable content.

reasondropped when
content_emptythe page is empty / whitespace only
auththe URL is an auth host/path (whole-segment match, e.g. accounts.google.com, /login, /oauth2) or a content-light page contains a password field
redirecta content-light page whose only job is a meta-refresh or a client-side location change
kepteverything else — articles, docs, nav/aggregator lists, even non-HTML — is captured

The auth and redirect checks only fire on content-light pages, so a real article whose chrome embeds a login or newsletter form, or that carries an auto-refresh, is kept. The gate never throws on unusual input. Per-decision counts (captured vs dropped, by reason) accumulate in gate_metrics.ts and are surfaced by the bergamot.showCaptureMetrics command.

3The stored record — PageCapture

webpage_capture is the single canonical per-page record: the lossless raw page plus cheap metadata, keyed by page_session_id (the stable id the RAG pipeline's chunks foreign-key to). The raw page is the durable source of truth for everything downstream.

  • Write: store_capture() compresses the page (zstd, @mongodb-js/zstd), reads <head> metadata, and upserts via insert_webpage_capture() (ON CONFLICT (page_session_id) DO UPDATE, so a re-capture overwrites cleanly). The metadata view is PageCapture (page_capture_models.ts); navigation-tree queries read the title from webpage_capture.
  • Read (parent document): read_capture(db, page_session_id) decompresses content_compressed back to the original HTML. This is the read path the RAG-prep pipeline uses; it is exposed over HTTP as /query/capture_content and surfaced by the MCP get_webpage_content tool.
  • Round-trip: compress → store → decompress is byte-identical (asserted in store_capture.test.ts and the deterministic capture_eval.test.ts over committed fixtures).

4What ingest does not do

Ingestion writes only to DuckDB webpage_capture. There is no main-content extraction, no chunking, no embedding, no summarisation, and nothing is written to any vector store. LanceDB is fully decoupled from the capture and query flow; semantic search returns nothing until the RAG-prep pipeline builds its index. All of that interpretive work lives in the RAG-prep pipeline (task-31), which reads stored raw pages and is free to re-run over the whole corpus and be tuned against a retrieval harness rather than baked irreversibly into capture.

No interim embedding. Ingestion writes nothing to a vector store, so captured pages are not semantically searchable until task-31 builds the index. This keeps capture pure and avoids throwaway code. The LLM client abstraction and any model configuration are reintroduced by task-31 when the pipeline actually calls a model; capture itself needs neither.

5Module map

Capture is a small set of single-purpose modules under vscode/src/:

ModuleResponsibility
workflow/page_capture_pipeline.tsrun_page_capture(deps, inputs) — orchestrates gate → store → record outcome

workflow/read_metadata.tsread_metadata(html, url) → PageMetadata — cheap <head> parse

workflow/gate_metrics.tsprocess-wide captured/dropped counters (module accumulator, not a class)
page_capture_models.tsPageCapture / PageActivitySessionWithMeta schemas
duck_db.tswebpage_capture table + insert_webpage_capture / get_webpage_capture / get_webpage_capture_bytes + tree queries

The visit queue (visit_queue_processor.ts) holds the CaptureDeps and calls run_page_capture; the server (server/server_manager.ts) builds the deps from its DuckDB handle. There is no stateful workflow class and no LLM client in the capture path.

6Cost

Ingest cost: zero

No LLM tokens, no network, no per-page model cost at capture — down from up to four LLM calls per page (classify · content-processing · analysis · tree-intentions) in the previous categoriser.

Storage cost: a few hundred KB / page

The raw page is stored zstd-compressed. Cheap, and the price of being able to re-index the whole corpus at will.

Model cost lives in RAG

The only model spend is the RAG-prep pipeline (task-31), run deliberately over the corpus and measured on a harness — not silently on every page view.

Invariants. Ingestion makes zero LLM calls and is fully deterministic and offline. The raw page (zstd) plus cheap <head> metadata is the canonical record; there is no LLM-derived analysis, summary, or intentions, and no vector write at capture. Schema changes are applied by a destructive dev-DB reset (see backlog/docs/dev-db-reset.md) — no migrations, no backwards-compatibility shims.
