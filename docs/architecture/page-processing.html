📥 Page Processing

How a captured visit becomes a stored record. Ingestion is pure, lossless metadata capture with zero LLM calls: visit metadata is stored, and page content is acquired separately by re-downloading the public URL during post-processing.

visit → deterministic gate → store metadata  ·  (no LLM, no network)

Page processing is the stage inside the VS Code extension that turns a captured visit into a durable record. The organising idea is to separate capture from content acquisition. Capture is deterministic and lossless — it persists browsing metadata only (visit id, URL, page-load timestamp, title from the tab, and the navigation/session graph) and makes no LLM calls at all. Page content is never captured. It is obtained later, during post-processing, by re-downloading the page from its stored public URL; everything interpretive — isolating the article, chunking, embedding, summarising — is the job of the RAG-prep pipeline (task-31), which reads the re-downloaded public pages on its own schedule and can re-run over the whole corpus with better algorithms.

Why metadata, not the page? Capture is separated from content acquisition. Metadata is the durable source of truth; content comes from re-downloading the public URL on demand. The login wall is the privacy filter — pages behind authentication fail to re-download and are excluded automatically, so no sensitive page bytes are ever stored at capture. Re-download fidelity caveat: a re-downloaded page is not guaranteed to equal the page as viewed — dynamic/JS-rendered content, dead links, paywall/consent drift, A/B variants, and edits over time all diverge. Citations reference the URL and metadata, not a byte-for-byte snapshot.

1The capture pipeline

Capture is a short, fully deterministic path orchestrated by run_page_capture(deps, inputs) in vscode/src/workflow/page_capture_pipeline.ts — a plain function over an immutable CaptureDeps struct, not a stateful class. For each visit it runs the relevance gate; for kept visits it stores the visit metadata (URL, title, timestamp). No page content is read, no model is ever called, and nothing is written to a vector store.

Navigation-tree linking (referrer → tree) happens upstream in the visit queue (webpage_tree.ts) before the pipeline runs, and is independent of the keep/drop decision — every visit gets a tree node; only the capture is gated.

Metadata source of truth

Visit metadata (URL, title, timestamp, navigation graph) is stored losslessly in DuckDB and is the durable source of truth. Page content is acquired later by re-downloading the public URL.

Title from the tab

Title and URL are read directly from the tab at capture — no page body needed. The <meta>-derived fields (site, author, published, language) are parsed later from the re-downloaded page.

Zero LLM, zero failure surface

Ingestion makes no network call and cannot fail on auth, prompt-length, or non-JSON. It is the cheapest, most robust path; all model cost lives in the RAG pipeline where it is gated.

2The capture gate

evaluate_page_gate(visit) (vscode/src/workflow/page_gate.ts) returns a GateDecision {keep, reason} from cheap, deterministic signals over metadata — no LLM, no topic taxonomy, no content inspection (there is no content to inspect). Incognito tabs are refused before any capture request is made. The gate is deliberately permissive: it keeps the visit and records its metadata. There is no ingestion-time sensitivity heuristic and no content denylist — the privacy exclusion is enforced by the login wall at re-download time.

Empty, auth, and redirect interstitials cannot be judged at capture, because there is no content to inspect. Dropping them moves to re-download time: a fetch that yields a login wall, redirect stub, or empty body is discarded there, and the auth-walled visit remains as trail/metadata only. An optional URL-pattern skip may avoid re-downloading obvious auth/redirect hosts. The gate never throws on unusual input. Per-decision counts accumulate in gate_metrics.ts and are surfaced by the bergamot.showCaptureMetrics command.

3The stored record — PageCapture

webpage_capture is the single canonical per-page metadata record, keyed by page_session_id (the stable id the RAG pipeline's chunks foreign-key to). It holds metadata only and is the durable source of truth for everything downstream. Page content is re-downloaded from the URL on demand.

  • Write: store_capture() persists the visit metadata (URL, title, timestamp) and upserts via insert_webpage_capture() (ON CONFLICT (page_session_id) DO UPDATE, so a re-capture overwrites cleanly). The <meta>-derived fields are filled in later from the re-downloaded page. The metadata view is PageCapture (page_capture_models.ts); navigation-tree queries read the title from webpage_capture.
  • Read (content): page content is acquired by re-downloading the stored URL during post-processing. Cached re-downloaded content (a separate encrypted tier) is the read path the RAG-prep pipeline uses; it is exposed over HTTP as /query/capture_content and surfaced by the MCP get_webpage_content tool, and may be unavailable for login-walled or dead pages.

4What ingest does not do

Ingestion writes only metadata to DuckDB webpage_capture. It reads no page content, performs no re-download, no main-content extraction, no chunking, no embedding, no summarisation, and nothing is written to any vector store. Content acquisition (re-download), Temporal Topic Detection, and the RAG-prep pipeline (task-31) all run downstream over the re-downloaded public corpus, on their own schedule, tuned against a retrieval harness rather than baked irreversibly into capture.

No interim embedding. Ingestion writes nothing to a vector store; the clusterable and searchable corpus is the re-downloadable public subset, not visited at capture time. Visits whose pages fail to re-download (auth-walled, dead) remain as trail/metadata only and are excluded from clustering and retrieval. The LLM client abstraction and any model configuration are reintroduced by task-31 when the pipeline actually calls a model; capture itself needs neither.

5Module map

Capture is a small set of single-purpose modules under vscode/src/:

ModuleResponsibility
workflow/page_capture_pipeline.tsrun_page_capture(deps, inputs) — orchestrates gate → store metadata → record outcome
workflow/page_gate.tsevaluate_page_gate(visit) → GateDecision — the deterministic capture gate over metadata
workflow/read_metadata.tsread_metadata(html, url) → PageMetadata — cheap <meta> parse over re-downloaded content
workflow/store_capture.tsstore_capture() — persist visit metadata to DuckDB
workflow/gate_metrics.tsprocess-wide captured/dropped counters (module accumulator, not a class)
page_capture_models.tsPageCapture / PageActivitySessionWithMeta schemas
duck_db.tswebpage_capture table + insert_webpage_capture / get_webpage_capture + tree queries

The visit queue (visit_queue_processor.ts) holds the CaptureDeps and calls run_page_capture; the server (server/server_manager.ts) builds the deps from its DuckDB handle. There is no stateful workflow class and no LLM client in the capture path.

6Cost

Ingest cost: zero

No LLM tokens, no network, no per-page model cost at capture. Capture reads only the tab's metadata.

Storage cost: a few bytes / visit

Only visit metadata is stored — URL, title, timestamps. No page bytes at rest in the metadata store.

Model cost lives in RAG

The only model spend is the RAG-prep pipeline (task-31), run deliberately over the re-downloaded corpus and measured on a harness — not silently on every page view.

Invariants. Ingestion makes zero LLM calls, captures browsing metadata only, and is fully deterministic and offline. The visit metadata is the canonical source of truth; no page content is stored at capture, and there is no LLM-derived analysis, summary, or vector write at capture. Content is re-downloaded from the public URL on demand. Schema changes are applied by a destructive dev-DB reset (see backlog/docs/dev-db-reset.md) — no migrations, no backwards-compatibility shims.
