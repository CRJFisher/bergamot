🧩 VS Code Extension

The backend host. It activates the ingest server, durable queue, and the deterministic zero-LLM metadata-capture pipeline; owns the DuckDB metadata store; runs the re-download/post-processing subsystem; and spawns the MCP server. This is where a visit becomes a durable metadata record.

vscode/src · extension.ts activate() · TypeScript

1Activation

On activation, extension.ts wires the system together in order:

  • Database — DatabaseManager.initialize_all() opens DuckDB (the metadata store — the durable source of truth). No vector store is opened at ingest.
  • Ingest server — ServerManager.start() binds the first free port in 5000–5009 and writes it to ~/.bergamot/port.json.
  • Commands — CommandManager.register_all() registers the webpage hover provider, the right-to-forget command (Bergamot: Forget — delete by URL, origin, or time range, cascading across the metadata store and the encrypted content cache), and the dev observability/replay commands.
  • Re-download / post-processing — the content subsystem reads stored URLs, re-downloads the public pages (login-walled pages fail and are excluded), and feeds Temporal Topic Detection then the RAG-prep pipeline.
  • MCP server — MCPServerManager.start_deferred(2000) spawns the standalone MCP subprocess after 2 s (non-blocking).

3Reception: durable ingestion

The server acknowledges the browser immediately, then processes asynchronously — no visit is lost on restart.

StageWhat happens
POST /visitHash url:page_loaded_at → session ID; validate the metadata payload against a Zod schema.
InboxWrite the visit to {globalStorage}/visit_inbox/{id}.json (durable) before returning 200.
QueueVisitQueueProcessor drains the inbox in batches (size 3 or 1 s timeout) with retry.
CleanupOnce the visit is persisted to DuckDB, its inbox JSON file is removed. Orphans are reloaded on startup.

4Capture: run_page_capture

The pipeline in workflow/page_capture_pipeline.ts turns a captured visit into a durable, lossless metadata record with no LLM call. It is a plain function taking the DuckDB handle directly (no stateful class). There is no capture gate — every non-incognito visit's metadata is stored.

No page content is read, no model is called, and nothing is written to a vector store. Title and URL come directly from the tab. Page content is acquired downstream by re-downloading the public URL; the <meta>-derived fields, summary, topics, chunking and embedding are all handled by the re-download subsystem and the RAG-prep pipeline (task-31), which run over the re-downloaded public corpus.

5Navigation trees

Visits are organized into trees — one per browsing session — using the referrer chain captured by the browser extension. A page with a known referrer is attached as a child of the tree containing that referrer; a page without one starts a new tree. Tree construction runs in the visit queue, independent of the capture gate: every visit gets a tree node, while the gate decides separately whether the page is captured.

Single-writer discipline. Only the extension writes to DuckDB. Every other consumer (MCP server, external scripts) reads through the HTTP query API, which keeps the embedded database safe from concurrent access.
