🔌 MCP & Query Layer

How AI agents and scripts reach the knowledge base. A standalone MCP server provides five deterministic tools, all backed by a read-only HTTP API over DuckDB. Semantic search is reintroduced by the RAG-prep pipeline (task-31).

mcp_server_standalone.ts · /query/* · stdio transport

1Topology

The MCP server runs as a separate subprocess spawned by the extension. Because DuckDB is single-writer, the MCP server never opens it directly: every tool proxies over HTTP to the extension's own server, which owns the writer. The MCP server opens no store of its own.

3HTTP query API

The same Express server that ingests visits also serves read-only queries. External scripts can hit these directly — the extension is the gateway to DuckDB.

EndpointPurpose
GET /statusHealth check + { service: "bergamot" } identity marker (used by browser discovery).
POST /visitIngest a captured visit (metadata only — no page content). Covered in VS Code Extension.
GET /query/visit_by_url?url=Exact-URL lookup of the most recent visit.
GET /query/page_by_title?title=Exact-title lookup → capture metadata.
GET /query/tree?tree_id=All pages in a navigation tree, with capture metadata.
GET /query/recent_trees?limit=Most recently modified trees with member pages.
GET /query/capture_content?page_session_id=The re-downloaded (possibly cached) page content; unavailable for login-walled or dead pages.

4Discovery & security

  • The extension writes its chosen port to ~/.bergamot/port.json; the MCP subprocess reads it to find the query API.
  • CORS is pinned to chrome-extension:// origins (and origin-less callers like curl/scripts); ordinary web pages are blocked.
  • POST /visit carries a small metadata JSON body — no compressed page content — so the request stays lightweight.
  • The MCP subprocess needs no store credentials — it only needs the port file to reach the query API.
Why proxy every query? DuckDB is embedded and single-writer. Rather than risk a second process opening the database file, the MCP server asks the extension — which owns the writer — over HTTP for everything, including the re-downloaded page content.
