💾 Storage Layer

Ingestion uses one store: DuckDB. It holds the browsing-metadata record — the durable source of truth. Any re-downloaded content is a separate encrypted on-demand tier; vector search is the job of the RAG-prep pipeline (task-31).

duck_db.ts · webpage_categorizations.db · content_cache.db

1One store at ingest

Capture is DuckDB-only. DuckDB is the authoritative metadata record of what was visited and how visits relate — the durable source of truth. It stores no page content: only visit metadata (URL, title, page-load timestamp) and the navigation/session graph. It is single-writer (the VS Code extension owns the connection); other processes read through the server's HTTP query endpoints (see MCP & Query).

DuckDB — metadata source of truth

Visits, navigation trees, and per-visit metadata (URL, title, timestamps). No page bytes. Fast analytical queries; single-writer. Encrypted at rest with DuckDB native encryption — the key lives in the OS keystore via VS Code SecretStorage, the file is only ever created encrypted, and key loss means the store is unrecoverable (no plaintext fallback; see docs/threat-model.md).

webpage_categorizations.db · encrypted at rest

Content cache — separate encrypted tier

Content is obtained later by re-downloading the public URL. Cached re-downloaded content lives in its own encrypted DuckDB store (content_cache.db) under the storage base, with its own OS-keystore key — never the source of truth and never inside the syncable metadata store; in dev it lives in the gitignored, unpackaged .dev-storage/, and if the surrounding directory is ever backed up or synced the file rides along as ciphertext — encryption, not location, is the load-bearing defense. It is populated only when a consumer opts in through CachedCorpus with a named scope (TDT, task-36.3, when it lands); the default read path re-downloads live. The right-to-forget cascade (right_to_forget.ts, surfaced as Bergamot: Forget) deletes from the cache — by session id, by URL, and by origin — and never creates or populates it. Scopes attribute entries, they do not partition them — re-caching under a new scope reassigns the row. Every item is per-item deletable for the right-to-forget cascade.

content_cache.db · on-demand · encrypted · scoped

Vector search — deferred

Semantic search is the job of the RAG-prep pipeline (task-31): it chunks and embeds the re-downloaded public pages into a vector index on its own schedule. Ingestion writes no embeddings.

TableGrainHolds
webpage_trees1 row / browsing sessionTree id + first/last activity timestamps.
webpage_activity_sessions1 row / page visitURL, referrer + referrer session id, load time, owning tree.
webpage_capture1 row / visitPer-visit metadata only: page_session_id, URL, title (captured directly from the tab), content type, and capture timestamp. No page content. The canonical per-page metadata record.
webpage_fetch1 row / re-download attemptAppend-only fidelity log of the re-download fetcher: outcome classification (ok / auth_redirect / forbidden / paywall / dead_link / non_html), final URL, HTTP status, content hash, fetch timestamp, and the <meta>-derived fields. No page content.

webpage_capture has no foreign key on page_session_id, so a capture can be written before (or independently of) its activity-session row. Tree queries LEFT JOIN webpage_capture to read a page's title. The title and URL are captured directly from the tab; the <meta>-derived fields (site, author, published, lang) are not stored here — they are parsed from the re-downloaded page and logged to webpage_fetch.

Canonical record: webpage_capture is the single per-page metadata record — page_session_id, URL, title, content type, and capture timestamp. It holds no page content and no <meta>-derived fields; content and those fields come from re-download (logged to webpage_fetch), and any content cache is a separate encrypted tier. Schema changes are applied by a destructive dev-DB reset (backlog/docs/dev-db-reset.md) — no migrations, no backwards-compatibility shims.
