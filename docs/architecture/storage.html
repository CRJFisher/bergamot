💾 Storage Layer

Two complementary stores, deliberately kept separate: DuckDB for relational records, and LanceDB for vector search.

duck_db.ts · lance_db.ts

1Why two stores

DuckDB — relational

The authoritative record of what was visited and how visits relate. Fast analytical queries over visits, trees, and analysis. Single-writer.

webpage_categorizations.db

LanceDB — vectors

Semantic search. Stores page content and its embeddings; supports vector + keyword (BM25/FTS) search with pluggable rerankers.

webpage_memory.db

TableGrainHolds
webpage_trees1 row / browsing sessionTree id + first/last activity timestamps.
webpage_activity_sessions1 row / page visitURL, referrer + referrer session id, load time, owning tree.
webpage_analysis1 row / visitLLM-derived title, summary, intentions.
webpage_tree_intentions1 row / (tree, visit)Intentions recomputed with full tree context.

4Vector store (LanceDB)

AspectDetail
ClassLanceDBMemoryStore in lance_db.ts
Namespacewebpage_content (page content + embeddings)
Operationsput (auto-embed), get, search({query, limit, filter}), batch()
EmbeddingsLocal all-MiniLM-L6-v2 (384-dim, via @xenova/transformers), cached in memory
CachingEmbedding cache (≤1000 entries, 5-min expiry), search-result cache, table cache (bounds memory)
Locked decision: the two stores stay separate — they are not collapsed into one. DuckDB answers "what and how related", LanceDB answers "what's similar". Each is the right tool for its question. (Markdown was removed as a store in the lean-core purge.)
