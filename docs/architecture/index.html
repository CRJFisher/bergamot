Bergamot

Capture browsing metadata as you browse, re-download the public pages later, and expose the result to AI agents via MCP for PKM workflows.

Browser extension → VS Code backend → DuckDB (metadata) → re-download → TDT → RAG / MCP

Bergamot captures browsing metadata only as you browse — visit id, URL, page-load timestamp, title, and the navigation/session graph — never page content. That metadata is the durable source of truth, recorded by a deterministic, zero-LLM capture pipeline. Page content is obtained later by re-downloading the public URL during post-processing; pages behind a login wall fail to re-download and are excluded automatically. The system has two deployable artifacts — a Chromium browser extension (capture) and a VS Code extension (gate, store, serve, re-download) — that communicate over a single local HTTP transport. Over the re-downloaded public corpus, Temporal Topic Detection runs first, then the RAG-prep pipeline (task-31).

2The four subsystems

🌐 Browser Extension →

Chromium MV3 extension. Reads the visit's title/URL/timestamp and maintains the cross-tab navigation session graph, then posts metadata-only visits to the backend over HTTP. No page content is captured.

content.ts · background.ts

🧩 VS Code Extension →

The backend host. Runs the Express ingest server, durable inbox, batch processor, and the deterministic zero-LLM capture pipeline that gates and stores each visit's metadata and builds navigation trees, plus the re-download/post-processing subsystem.

extension.ts · run_page_capture

💾 Storage Layer →

DuckDB holds the metadata record — the durable source of truth. Any re-downloaded content is a separate, encrypted, on-demand tier. Vector search is reintroduced by the RAG-prep pipeline (task-31).

DuckDB

🔌 MCP & Query →

The access layer. A standalone MCP server plus a read-only HTTP query API expose the knowledge base to AI agents and external scripts.

5 MCP tools · /query/*

🔎 RAG Pipeline →

Runs over the re-downloaded public corpus, after Temporal Topic Detection: the phased upgrade plan of hybrid search, contextual chunking, reranking, and an evaluation harness to measure each step.

re-download → chunk → embed → retrieve → rerank

    U->>C: navigates to page

    C->>B: sendMessage(visit metadata)
    B->>B: enrich with referrer, group_id, opener
    B->>S: HTTP POST /visit (discover port 5000–5009)
    S->>Q: persist to inbox, enqueue, return 200
    Note over B,S: browser is acknowledged immediately
    Q->>Q: assign to navigation tree (webpage_tree)
    Q->>W: run_page_capture(visit metadata)
    W->>W: deterministic gate (keep/drop, no LLM)
    W->>DB: store visit metadata (source of truth)
    W-->>Q: remove inbox file (durably ingested)
    R->>DB: read stored URLs
    R->>R: re-download public page (login wall excludes private) → TDT → RAG

Locked decisions: ingestion is a deterministic, zero-LLM capture pipeline — it stores browsing metadata only (visit id, URL, page-load timestamp, title, navigation/session graph) in DuckDB, which is the canonical source of truth; page content is never captured. Content is obtained later by re-downloading the public URL, where the login wall excludes private pages; Temporal Topic Detection runs first over that public corpus, then the RAG-prep pipeline (task-31). Storage at ingest is DuckDB only; transport is a single HTTP server on a dynamically-discovered port; the browser side is Chromium-only; e2e tests run on Playwright against a mock capture server. Schema changes are destructive dev-DB resets — no migrations, no shims.
